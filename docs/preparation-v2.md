# Проработка требований v2

Новые задачи Runner используют v2: ИИ предлагает требования и сценарии, человек решает существенные развилки и подтверждает требования вместе с планом. Семь этапов сохранены; к исследованию, вопросам и плану можно возвращаться без создания нового витка.

## Поведение

- До исследования нужны цель, проблема и границы. Открытые вопросы к реализации допускаются; `[исследование]` блокирует сам поиск.
- Перед реализацией каждый `claim-N` имеет наблюдаемое поведение и процедуру с ожидаемым результатом. В intent v2 модель передаёт лист приёмки и основания как JSON-массивы со строгими полями; Runner проверяет ID и сам рендерит Markdown-таблицы, поэтому модель не управляет их разметкой.
- Каждый этап получает только свои входные артефакты. Общий контекст не дублирует intent, отчёт разведки, ответы и план; для продолжения передаются только предыдущие claim-N, ответы человека или замечания проверяющего, которых нет во входных файлах этапа.
- На этапах intent, explore и plan модель отвечает на структурированные поля; Runner проверяет значения и сам собирает документы. Для приёмочных требований и оснований intent используется JSON с проверяемыми ID. На explore Runner передаёт исходники и тесты карточками, а план обязан ссылаться на полученные факты. Модель не редактирует эти артефакты напрямую.
- Нет квот по числу требований и `[edge]`. Даже малый контур проходит предварительное исследование; глубина определяется неопределённостью и последствиями.
- `intent.md` содержит актуальные требования. Ответы человека сохраняются дословно в `clarification-report.md`, а изменения требований отражаются в плане. Ответ может уточнять claim, границы, подход или инварианты.
- Проверка плана делает два свежих вызова по маршруту verify: независимое понимание первоисточников, затем сравнение с требованиями и планом. Журнал исполнителя и его план отсутствуют в первом вызове. Инструменты отключены; рантайм передаёт адресованные исходники через безопасный индекс, с явными ограничениями объёма.
- Незавершённая проверка, существенные замечания и изменение источников не допускают одобрения. Это проверка модели, она не доказывает полноту требований.
- Интерфейс перед одобрением показывает актуальные требования и отличия от последней одобренной редакции. Одобрение связано с показанной редакцией, требованиями, ответами и содержимым плана. Изменения требуют повторной проработки и подтверждения.

## Хранение и совместимость

`preparation.json` рядом с `intent.md` содержит версию 2, дословные исходные запросы, независимый разбор, замечания и историю одобренных редакций. Модель не может записывать этот файл. Он включается в коммит витка, поэтому история переживает перенос проекта. Читаемые Markdown-документы сохраняются.

Существующие витки без этого файла остаются на v1. `POST /api/runs/:id/stages/intent/run` принимает `preparationVersion: 1 | 2`; выбор действует только до создания первой задачи. По умолчанию новый Runner использует 2. Режим v1 сохраняет заполнение полей и специальные конвейеры для ограниченных моделей. V2 использует связный анализ с инструментами на этапах проработки; заполнение по полям, дозаполнение осей и StepExecutor отключены, чтобы полный контекст согласованных требований доходил до исполнителя.

`GET /api/runs/:id` возвращает необязательное поле `preparation`: редакция, подтверждение, готовность к одобрению, замечания, текущие требования, различия и fingerprint. Для одобрения плана v2 `POST /decision` требует `preparationFingerprint` из показанного ответа. Старые клиенты могут продолжать v1.

Текст профиля поставляется в `server/methodology/preparation-v2.md`; установленный `profiles/preparation-v2.md` эталона имеет приоритет. Установка: `node tools/install-preparation-profile.mjs <каталог-эталона>`. Скрипт добавляет профиль и ссылку из SDLC.md, не заменяя правила v1. При отличающемся установленном профиле останавливается для сверки. Терминальные скиллы v1 не исполняют протокол v2; такие витки следует продолжать в Runner.

## Проверка качества

Юнит-тесты проверяют переходы, изоляцию контекста критика, отказ при невалидном ответе, историю редакций и снятие одобрения при изменениях. Старые эталонные прогоны явно выбирают v1; ожидаемые артефакты не переписываются ради нового режима.

Проверка подготовки отдельно оценивает, сколько раз модель получила дублирующие артефакты, сколько исправлений потребовалось и дошла ли она до проверяемого плана. Частичный артефакт при исчерпании бюджета сохраняется; незавершённый прогон не считается успешным.

Стенд сохраняет v1 по умолчанию. Для сравнения запускать одну модель и одинаковые задачи с `--preparation-version 1` и `--preparation-version 2`, минимум пять повторов, начиная с intent без старого снимка. Остановку на плане задаёт `--stop-after-stage plan`. Пример:

```sh
npm run bench -- --all --model <model-id> --task two-right-answers --preparation-version 2 --stop-after-stage plan --repeat 5 --keep-workspace
```

Оценку смысла делает отдельный проверяющий по эталону, составленному до знакомства с планом: потерянные и придуманные требования, неразрешённые неоднозначности, лишние вопросы, обнаружение неправильных реализаций. Время человека, стоимость и возвраты брать из метрик запуска. Ответы автоматического прокси не являются измерением времени живого пользователя.

Набор сценариев и ожидаемые различия — `bench/diagnostics/preparation-cases.json`. Зелёные структурные тесты не заменяют сравнения качества на живых моделях; такие результаты не заявляются автоматически.
