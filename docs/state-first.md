# Каноническое состояние и независимая приёмка

Режим включается явно для нового витка через `stateFirst: true` при запуске intent
либо операторским `POST /api/runs/:id/state/enable`. Старый виток можно перевести
в этот режим явно: исходные Markdown-артефакты архивируются, требования становятся
uncertain, прежний зелёный вердикт не переносится. План нужно подтвердить заново.

## Источник состояния

`.sdlc/<slug>/state.json` соответствует `agent-sdlc/state/v1`: требования, гейты,
попытки, решения и JSON-ревью. Решения принимает оператор через существующий
`POST /decision`, результаты команд и вердикт записывает рантайм. Модель не имеет
права менять state, манифест приёмки и `state-evidence/`.

Запись атомарна. Внешний журнал транзакции и квитанция хэша находятся в
`SDLC_STATE_DIR/contracts/`, вне проекта. После прерывания восстанавливаются только
известные старые или новые байты транзакции. Неизвестная внешняя правка, удаление,
чужой slug, некорректный JSON и несовпавшая квитанция блокируют работу; перехода
к Markdown или старому вердикту нет.

`GET /api/runs/:id/state` возвращает каноническое состояние. Номер chunk/attempt
после рестарта восстанавливается из него. Новый chunk, новая попытка и новый Verify
снимают положительный результат до завершения свежей проверки. Markdown-отчёт
приёмки — проекция, его строка `passed` не меняет решение.

State, манифест и `state-evidence/` включаются в локальный коммит. Внешняя квитанция
и исполняемый защищённый набор привязаны к машине: копирование state на другую
машину само по себе не переносит доверие к результату.

## Подготовка приёмки

Независимый проверяющий готовит тесты по одобренным требованиям, до изменения
кандидата. Набор находится вне проекта разработчика. Его происхождение и
квалификацию подтверждает оператор; имя модели само по себе не доказывает качество.
Этот API не предоставляется как инструмент модели.

После одобрения плана оператор вызывает:

```http
POST /api/runs/:id/acceptance
Content-Type: application/json

{
  "sourceDir": "/absolute/path/to/reviewer-suite",
  "image": "node:20-alpine",
  "author": { "kind": "human", "id": "Independent reviewer" },
  "qualification": "Набор подготовлен по согласованному контракту и проверен на дефекте",
  "checks": [{ "claimId": "claim-1", "file": "behavior.test.mjs", "name": "observable behavior" }],
  "limitations": "Проверяются входы и результаты публичного API"
}
```

Для отдельной модели `author.kind` равен `model`, а `id` — `provider:model`;
совпадение с исполнителем Chunk отклоняется. Каждый автоматический claim должен
быть покрыт. `[manual]` учитывается только как тег ячейки ID в исходной приёмке.
Наборы полностью ручной приёмки этим исполнителем не поддерживаются.

Тест получает корень снимка через `process.env.SDLC_CANDIDATE_ROOT`. Допустимы
явные `.test.mjs`, `.spec.mjs`, `.test.cjs`, `.spec.cjs` внутри набора. Симлинки,
выходы из корня и чрезмерные снимки отклоняются. Docker-образ должен уже быть
установлен; при фиксации сохраняется его неизменяемый ID, загрузки из сети нет.

Runner копирует набор в своё внешнее хранилище, фиксирует SHA-256 всех файлов,
требований и плана, затем исполняет baseline. Красный baseline для нового поведения
допустим; отсутствие реального прогона — нет. Имена проверок должны появиться в
событиях test-runner и при красном baseline: определяй тест до обращения к кандидату,
а импорт ещё не существующего модуля выполняй внутри теста. Baseline, его вывод и время сохранены.
Без зафиксированного набора Chunk не начинается. Изменение требований, плана или
набора требует новой фиксации; изменение теста — отдельная работа проверяющего,
изменение ожидаемого поведения — новое решение человека.

## Исполнение

Обычные Node-команды гейтов и независимая приёмка исполняются в одноразовых
контейнерах: без сети и Docker socket, от непривилегированного пользователя,
с ограничениями CPU, памяти, числа процессов, времени и объёма вывода. Корень
контейнера, снимок кандидата и набор доступны только для чтения; `/tmp` — отдельный
ограниченный scratch. Отмена и timeout удаляют контейнер до освобождения снимка.

Модель работает через разрешённые инструменты чтения и правки; Bash и MCP в этом
режиме не выдаются. Локальный коммит остаётся отдельным действием рантайма через
существующее одобрение. Проектные контейнеры с warmup и Docker socket не используются.
Нет Docker или не поддерживается команда — проверка не становится зелёной, запуска
на хосте вместо контейнера нет.

После изменения кода Verify запускает независимый набор и сохраняет отдельный
гейт «Независимая приёмка». Нужны реальный код выхода и непустой тестовый прогон
без пропусков, отмен и провалов. Каждая именованная проверка из манифеста должна
присутствовать в событиях test-runner с адресом файла защищённого набора; stdout
кандидата и ранний `process.exit(0)` не заменяют выполнение проверки.
Результат связан с полным снимком кандидата,
хэшами контракта и набора, ID образа и выводом. Ручная правка кода после Verify,
включая новый файл, инвалидирует результат и закрывает handoff.

Для state-first требуется завершённое структурированное ревью по
`verify-review-v1` от маршрута, отличного от исполнителя. Неполный ответ и
противоречивое зелёное состояние не принимаются. Подписанная неприменимость гейтов
не выводится из свободного текста: схема v1 не содержит такой связи.

Первый адаптер поддерживает простые `node ...` команды от корня проекта, без
оболочки и eval. npm-скрипты, произвольные shell-команды, установка зависимостей,
нативные сборки и изменения файлов сборкой не заявляются поддержанными.
В снимок входят обычные отслеживаемые и неигнорируемые файлы Git, кроме `.git`,
`.sdlc` и `node_modules`; ignored-ресурсы и submodules требуют отдельного адаптера.
Снимок ограничен 100 MiB. Docker-изоляция не доказывает правильность самих тестов.

## Пробная симуляция

```sh
npm run bench:simulate -- --suite state-first --docker-image node:20-alpine
npm run bench:simulate -- --docker-image node:20-alpine --output ./simulation-report
```

Вторая команда запускает также три прежних набора. Новый набор проходит настоящий
Run с отдельными сценарными ответами модели: положительный контроль, неверный код
при модельном PASS, ранний process.exit(0), попытка переписать защищённый тест, рестарт, устаревший код,
повреждение state. Это проверка исполнения протокола, а не качества живой модели.
