# Закрытие задач: анализ флоу 04–05.10 и программа улучшений

Дата: 2026-10-05. Статус: частично реализовано; решения по пунктам — в разделе 10.

Документ собирает наблюдения за работой флоу 04–05.10 (серии `guided-sample-*`),
разбор мест, где задача не доходит до закрытия, и программу изменений —

## 1. Контекст: что происходило 04–05.10

- 04.10 — старт guided-режима: рантайм сам формирует bounded JSON-запросы вместо
  свободного tool-loop. ~20 проб с итеративными фиксами Plan/Intent/Chunk
  (журнал — `docs/guided-flow.md`). Вечером первый полный проход до Handoff.
- 05.10 — серии `guided-sample-20261005*` (≥8 парных): `zero-change-verify` и
  `add-validator` дошли до Handoff поодиночке (скрытые 7/7 и 8/8), но **парный
  повтор не воспроизвёл успех**: zero-change встала на Chunk (2/7), add-validator
  дошла до Verify, где независимое ревью дало честный красный.
- Заведены температурные профили GPT-OSS (`-low-t0-rf`, `-low-t02-rf`,
  `-medium-t02-rf`), порт LM Studio 1234→1434.
- Вся работа 04–05.10 не закоммичена (866 dirty файлов на `dashboard-zapuski`).

## 2. Как устроено закрытие сейчас

Флоу: `intent → explore → ask → plan → chunk → verify → handoff`
(`server/src/run/stages/index.ts:18`). Закрытие — цепочка:

1. зелёный вердикт verify с непротухшим патчем (`stalePatchReason`);
2. вход в handoff → рантайм делает локальный коммит (`stages/handoff.ts:499-531`);
3. модель заполняет `handoff.md`;
4. **человек подписывает «Приёмку»** (`handoff.ts:106`, `recordDecision`).

Красный вердикт → `retry` (новая попытка), `blocked_env` (та же попытка),
`escalate` (стоп). Продвижение сторожит `advanceProblem` (`Run.ts:1077`).

## 4. Изменения флоу (методология)

### F1. Эскалация = смена маршрута, а не стоп

Сейчас `escalate` — конец витка. Предлагается: при исчерпании бюджета попыток
или застрявших пунктах приёмки (`suggestEscalation.kind === 'suggest'`) виток
переходит в «паузу с опциями»:

1. **принять подъём модели chunk** — та же попытка продолжается на следующей по
   рангу модели (предложение уже считается в `escalation.ts`);
2. обрыв витка (`abortHandoff`) — как сейчас;
3. правка бюджета попыток в `.sdlc/gates.md` — как сейчас.

Решение остаётся за человеком (смена модели меняет стоимость и поведение), но
становится **действием в раннере**, а не ручной пересборкой прогона. Правило
фиксируется в `SDLC.md` и `server/methodology/guided.md`.

### F2. Бюджет средовых повторов

`blocked_env` по-прежнему не тратит номер попытки (методология сохраняется:
«средовый красный — не вина исполнителя»), но серия подряд `blocked_env`
ограничивается: умолчание 3, настройка в `.sdlc/gates.md` рядом с бюджетом
попыток. Исчерпание → `escalate` с причиной «среда». Устойчивый дефект среды
перестаёт быть бесконечным прогоном без прогресса.

### F3. Явные опции в блокерах продвижения

Каждый блокер `advanceProblem`/handoff обязан называть **все разблокирующие
действия**. Конкретно: при исчерпании попыток текст перечисляет три опции F1;
при протухшем патче — «повтори verify: он покраснеет по несовпадению diff↔дерево
и откроет новую попытку».

### F4. Второй шанс рецензенту verify

Сейчас repair-запрос рецензенту ровно один. Предлагается два: второй получает
сжатый контекст первой неудачи (что именно не разобралось в форме). Класс
«рецензент не смог оформить» перестаёт быть безусловно терминальным для витка;
класс «рецензент нашёл реальный дефект» не затрагивается.

## 5. Изменения реализации (код)

Каждый пункт — место, суть, критерий готовности. Порядок — по соотношению
эффект/риск.

### I1. Разблокирующие тексты блокеров (P3, реализует F3)

- `Run.ts:1077-1097` (`advanceProblem`): ветка `passed && stalePatchReason` →
  сообщение с явным действием («повтори verify»); ветка `escalate` → три опции
  из F1, включая «подъём модели — `POST /runs/:id/escalate`».
- `stages/handoff.ts:85` (`stalePatchReason` в блокере handoff): тот же явный
  совет.
- Критерий: тесты на тексты блокеров в `server/test/`; ни один блокер не
  оставляет оператора без названного действия.

### I2. Счётчик средовых повторов (P2, реализует F2)

- Состояние витка: `envRetries` (рядом с `attempt`); инкремент при
  `blocked_env`, сброс при любом другом вердикте (`Run.ts:1104-1128`).
- Порог из `.sdlc/gates.md` — парсер рядом с бюджетом попыток
  (`Run.ts:1238-1253`); умолчание 3.
- Исчерпание → вердикт `escalate` с причиной «среда не восстановлена за N
  прогонов» — дальше работает F1.
- Критерий: тесты — серия blocked_env до предела даёт escalate; смена вердикта
  сбрасывает счётчик; журнал итераций отражает причину.

### I3. Применение эскалации (P1, реализует F1; закрывает backlog
`model-escalation-in-run`)

- `Run.ts`: `applyEscalation(toModelId)` — подмена маршрута chunk в клоне
  профиля витка (клон создаётся в `Run.ts:619`), новая попытка на новой модели,
  событие в журнал витка (старое и новое id модели, застрявшие пункты).
- `server/src/index.ts`: ручка `POST /runs/:id/escalate { toModelId }`;
  доступна только при вердикте `escalate` или активном `suggest`; валидация —
  модель из `config/models.json`, ранг строго выше текущего.
- Правило рецензента: если рецензент verify слабее нового исполнителя —
  предупреждение в ответе ручки (не запрет: решение человека).
- `escalation.ts`: текст предложения дополняется именем ручки.
- Критерий: тесты — `applyEscalation` меняет маршрут и открывает попытку;
  ручка отказывает при зелёном/отсутствующем вердикте и при понижении ранга;
  предупреждение о слабом рецензенте присутствует.

### I4. Второй repair-запрос рецензенту (P4, реализует F4)

- `stages/verify/reviewer.ts:289-339`: лимит repair 1→2; второй запрос несёт
  сжатую выжимку первой неудачи (какие поля формы не разобрались).
- Критерий: тест на двойной repair; парная серия guided показывает снижение
  красных по «оформлению ревью» без роста ложных зелёных.

### I5. Мягкое истечение guided-бюджета (P5)

- `guidedState.ts` + `Run.ts:2352,2465`: за 5 минут до предела — предупреждение
  в следующий ответ модели («завершай текущий шаг»); по истечении — останов
  после текущего шага (не abort посреди запроса) с сохранением черновика и
  честной причиной (частично уже есть).
- Критерий: прогон с искусственно малым бюджетом завершается сохранённым
  черновиком и причиной «бюджет», без битых артефактов.

### I6. Синтаксис-страж черновиков chunk (P6)

- Перед применением правки из черновика — быстрая проверка парсабельности
  затронутого файла (по языку проекта); битый черновик отклоняется с
  `failedCheck: 'syntax'` до расхода предложения, подсказка про await/non-async
  уже существует — включается в отказ.
- Критерий: бенч-кейс с `await` в sync-callback отклоняется стражем, а не
  доезжает до verify.

### I7. Видимость ожидания человека (P7)

- В статус run — `awaitingSince` (timestamp входа в `awaiting`,
  `Run.ts:472-484`); CLI/веб показывают «ждёт оператора N мин».
- Критерий: поле в API статуса; отображение в списке прогонов. Автопринятие по
  таймауту **не делается** (модель ответственности; отдельно —
  backlog `auto-approve-rules`).

## 10. Решение по текущему коду (2026-10-05)

Реализованы подходящие независимые изменения:

- **I1/F3:** устаревший зелёный патч теперь даёт совет повторить Verify также при
  запросе новой попытки. Общая подсказка используется handoff и следующим chunk.
  Эскалация больше не описывается исключительно как исчерпание бюджета: её вызывает
  также отсутствие прогресса. Несуществующая ручка смены модели не рекламируется.
- **I4/F4:** максимум два repair-запроса свободному рецензенту. Повтор получает
  ошибки последнего ответа, его ограниченный фрагмент и требование сохранить дефекты.
  Каждый ответ проходит полный контракт отдельно; невалидные ответы остаются
  справочными, отказ запроса прекращает повторы. Конвейеры guided/reviewFill имеют
  собственные контракты и этим изменением не затрагиваются.
- **I7:** API списка и деталей витка отдаёт `awaitingSince`; список показывает
  время ожидания оператора. Повторный статус awaiting не обнуляет время; выход из
  ожидания очищает поле. Автоприёмки нет.

- **I2/F2:** реализован лимит серии средовых красных по завершённым прогонам Verify.
  По умолчанию третий даёт `escalate`. Счётчик хранится атомарно рядом с защищёнными
  вердиктами, переживает рестарт и не увеличивается от пересчёта внутри прогона.
  Другой исход и новый chunk сбрасывают серию. Номер попытки сохраняется после
  `blocked_env`. Итог используется вердиктом, отчётом и журналом; средовой escalate
  не добавляет проваленные пункты в историю смены модели.
  Настройка: `| Бюджет средовых повторов | да | вне витка | 3 |` в таблице «Набор».
  Проверка этого изменения: 57 профильных тестов и полный typecheck прошли.
  Дополнительно прошёл интеграционный сценарий через настоящий `Run.runStage`:
  `blocked_env → рестарт Run → blocked_env → escalate → восстановление → continue`.
  Подменная модель заполняет отчёт и проводит контрактное независимое ревью;
  сборочный скрипт реально запускается и имитирует недоступную зависимость кодом 127.
  Проверены сохранение попытки №1, согласованность вердикта/отчёта/журнала/событий,
  сброс счётчика и доступность Handoff после восстановления. Это тест рантайма,
  а не holdout качества локальных моделей.

Остальные пункты требуют уточнения проекта решения:

- **I3/F1:** rank — эвристика выбора, а не доказательство качества. Guided прямо
  требует одну локальную модель и не считает повышение её успехом. Предложение также
  противоречиво: F1 сохраняет попытку, I3 открывает новую при исчерпанном бюджете.
  Перед реализацией нужна отдельная политика бюджета после смены маршрута, выбора
  провайдера/параметров, ансамбля и сохранения маршрута после рестарта.
- **I5:** остановка только после текущего шага без ограничения длительности запроса
  отменяет гарантию бюджета. Нужны отдельный срок завершения текущего запроса и
  протокол безопасного сохранения частичного ответа; действующий лимит сохранён.
- **I6:** универсальная проверка синтаксиса требует зарегистрированных инструментов
  проекта. Также синтаксический отказ должен расходовать ограниченный бюджет запросов,
  иначе «до расхода предложения» создаёт бесконечный repair-цикл. Существующие проверки
  проекта и подсказки про await сохранены.
- **M1:** новые живые серии не запускались. Изменение свободного repair не является
  изменением guided-конвейера; показатели закрытия и ложных зелёных пока не измерены.

Добавлены регрессии для двух repair, исчерпания повторов, отказа запроса,
переходов ожидания и блокеров устаревшего зелёного патча.
