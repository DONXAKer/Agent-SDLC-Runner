## I. Форма ответа и адресация

### 1. Одна степень свободы на вопрос
Любая многоколоночная строка (ось, claim, находка) спрашивается **последовательностью закрытых вопросов**: сначала бинарный («затронута? да/нет») по всем строкам, затем ключ словаря по строкам с «да», затем адресат. Рантайм собирает строку сам. Закрывает: таблица осей (5/5), общий класс «строка из N колонок одним ответом». Опора: `FormFillExecutor` уже умеет карточку-поле, `matchChoice`/`matchAxisOutcome` — сопоставление ключа. Цена M. Мера: доля строк, разобранных рантаймом, до/после при той же модели.

### 2. Честный дефолт рантайма с пометкой для полей без владельца-человека
Поле схемы, у которого владелец не `human`, а модель дважды оставила пусто, закрывается значением-умолчанием **с явной подписью происхождения** («по умолчанию рантайма: не затронута шагами плана»). Прецедент уже есть — `defaultUnapprovedRecords` на handoff (§7.4). Закрывает: пустые клетки, «самоотчёт ≠ диск». Ограничение: `⏭`/«н/п с причиной» это не подменяет — подпись говорит, что причины нет. Цена S. Мера: число блокировок стража по пустым полям.

### 3. Механический кандидат в клетку: рантайм считает, модель подтверждает
Принцип предсортировки из `stage-tooling.md` §4 («рантайм считает, решение — нет») распространяется на все таблицы с семантикой «затронуто/не затронуто»: по `files_to_touch`, diff разведки, объявленным гейтам рантайм предлагает «вероятно да/нет» с основанием, модель отвечает согласием или правкой. Модель рассуждает от конкретных шагов, а не от абстрактной оси. Цена M. Мера: доля клеток, принятых без правки, и доля ложных «да».

### 4. Запись артефакта по ключу, а не по пути — на всех этапах-документах
На intent/explore/ask/plan модель не пишет свои артефакты через `Write`/`Edit` с путём: только инструмент с ключом артефакта (расширение `FillField`/`ArtifactKey`, тот же приём `PolicyContext.stageArtifacts`). Голое имя файла или опечатка в слаге становятся невозможными по построению, а не отклоняемыми. Закрывает: «запись вне плана» на документных этапах (gemma ×6, слаг `freesship`). Цена M. Мера: класс `запись вне плана` на этапах 1–4 → 0.

### 5. Единая функция полноты: страж завершения = предусловие следующего этапа
`intent` отчитался `ok`, а вход `plan` нашёл две дыры — значит, две разные проверки. Одна чистая функция «артефакт полон» на оба потребителя (как `axesGateRow` уже сделано для одного гейта). Закрывает: «самоотчёт ≠ диск». Цена S. Мера: число прогонов с `ok⚠` на этапе N и блокировкой на N+1 по тому же артефакту → 0.

### 6. Универсальный послеходовый обход дыр
Один общий `afterTurn`-хук для всех документных этапов: по каждой оставшейся дыре — карточный вопрос с нулевой историей (как `claimFill`/`planAxisFill`, но не по этапам, а по схеме). Сегодня добор существует россыпью (claims, files_to_touch, оси, explore) и каждый новый класс дыры ждёт своего топ-апа. Цена M (обобщение существующего). Мера: незакрытых мест после этапа на диске; число специальных топ-апов в коде.

### 7. Ремонт вызова с дельтой
Неразобранный вызов (нет обязательных аргументов) и «Read вместо Edit по плейсхолдеру» получают **один** ремонтный ход: рантайм возвращает схему инструмента, полученные аргументы и ожидаемое действие («ты прочитал файл — теперь `FillField ключ`»). Сейчас битый вызов = потерянный ход, за которым идёт цикл Finalize. Опора: `REPAIRS_PER_STEP` в `StepExecutor`, идея «ремонт без дельты бесполезен» (volume-insertion §2). Цена S. Мера: доля неразобранных вызовов, закрытых ремонтом.

### 8. Пагинация длинных списковых полей
Поле с минимумом ≥N записей (лист приёмки, карта файлов) спрашивается порциями («пункты 1–3», затем «4–6»), рантайм склеивает и нумерует. Снимает класс «обрезка на середине структуры» без подъёма `max_tokens`. Цена S. Мера: класс #7 (лимит длины) на списковых полях.

## II. Бюджет, контекст и время

### 9. Факты к полю: карточка несёт срез входа, инструменты выключены
Каждая карточка поля получает от рантайма ровно тот фрагмент входа, который нужен для ответа (текст задачи для «что делаем», список путей разведки для «что тронуть»), и **не имеет инструментов**. Модель, которая «читает шаблон вместо ответа» (ornith 400–800 с), физически не может уйти в разведку. Частично есть в `FormFillExecutor` (completion без цикла); обобщить на карточки во флоу `loop`. Цена M. Мера: время на поле, число Read на документных этапах.

### 10. Бюджет времени на поле, а не на этап
Таймаут уровня поля с деградацией: не ответил → повтор с укороченным вопросом → поле остаётся открытым, этап идёт дальше. Сейчас `stage-timeout` на 60-й минуте теряет всё, включая 40 закрытых полей. Цена S. Мера: доля этапов, закрытых частично вместо `stage-timeout`.

### 11. Режим рассуждения — ручка по классу вопроса
У thinking-моделей рассуждение выключается на карточных/закрытых вопросах и остаётся на свободном ходу. Подтверждение из журнала: reasoning-сиблинг встал там, где instruct прошёл при равных ручках. Реализация — параметр провайдера (`think`/`reasoning_effort`) по типу запроса, не по модели. Цена S. Мера: лимит длины на карточках у reasoning-моделей.

### 12. Adapter-блок вычитает фазы рантайма на каждом этапе
На verify adapter явно говорит «Phase 0/1/4.3 делает программа». На explore (конвейер), ask (вопросы задаёт рантайм), plan (засев `files_to_touch`, автозаполнение) — такого вычитания нет, и модель тратит ходы на инструкции, которые уже исполнены. Цена S (текст, `prompt/build.ts`). Мера: базовый промпт этапа в байтах; число ходов до первой записи.

### 13. Окно контекста — обязательное свойство модели для старта
Запись модели без `contextWindow` не стартует виток, с той же формулировкой «что именно задать», что `operatorProblem`. Один прогон test28d шёл без бюджета целиком. Цена S. Мера: класс «лимит длины без бюджета окна» → 0.

## III. Маршрутизация и конфигурация

### 14. Пакеты ручек по классу модели
Вместо записи на каждую комбинацию (`-stepfill-compactfill`, `-stepfill-axisfill`) — именованные пресеты («документные этапы карточками», «chunk по шагам»), выводимые из свойств модели (окно, ранг, локальность). test29 показал, что ручки взаимодействуют: снятие `compactForms` уронило gemma с plan на explore. Пресет измеряется как единица. Цена M (`config/profiles.ts`). Мера: число записей в `models.json`; воспроизводимость лучшего этапа между сериями.

### 15. Эскалация по полю, а не по этапу
Если поле дважды не закрылось на модели этапа, один вопрос по этому полю уходит на следующую по рангу модель профиля; этап остаётся за слабой. Карточка `model-escalation-in-run` описывает эскалацию этапа — здесь гранула меньше и дешевле. Цена M. Мера: доля этапов, закрытых без полной эскалации; стоимость.

### 16. Самоцензура как режим, не как вторая запись модели
Правило рецензента требует ранг строго выше; для self-review сейчас заводится двойник с рангом −1 руками (test28b упал на равных рангах). Режим `selfReview: true` в профиле, который рантайм честно помечает в отчёте («рецензент = исполнитель»), снимает класс конфигурационных срывов. Цена S. Мера: прогоны, не стартовавшие по рангу → 0.

## IV. Стенд и измерение

### 17. Средовой сбой — перезагрузка движка и продолжение того же этапа с диска
`ProviderEnvError` уже отличает среду от модели; состояние витка на диске. Недостающее звено — после N средовых ошибок подряд стенд зовёт `engine.ts` (уже есть в преполёте) и продолжает этап, а не завершает прогон `stage-env-repeat`. Цена S. Мера: доля прогонов с ⚠ среда.

### 18. Преполёт: вторая попытка пробы и вес устойчивости
Одиночный ❌ одной пробы краснил преполёт у 3 из 4 моделей, назавтра зелёных (test24c). Проба получает повтор; красным считается 2/2, а хронический ❌ одной пробы при зелёных остальных — предупреждение с рекомендацией `--no-preflight`. Уже назван кандидатом в журнале. Цена S. Мера: доля преполётов, опровергнутых прогоном.

### 19. В отчёте отделять «граница» от «адрес»
`classifyDenial` ставит ⚠️ ОПАСНА за запись в собственный артефакт по голому имени. Класс «адресация своего артефакта» (базовое имя совпадает с артефактом этапа) выделяется отдельно и из BOUNDARY_CLASSES исключается. Иначе матрица меряет опечатки как нарушения границ, и вердикт «опасна» обесценивается. Цена S. Мера: доля ОПАСНА, подтверждённых реальным выходом за проект.

### 20. Статистика отказов по ключу поля
Метрики витка (`metrics.json`) дописываются счётчиком «ключ поля → пусто/не из словаря/закрыто добором» по всем прогонам; bench сводит тепловую карту «поле × модель». Сегодня приоритет фиксов определяется по чтению журнала; карта покажет, что три модели падают на одном поле, до серии, а не после. Цена S. Мера: сама карта; время от находки до фикса.
