# Ошибки объёма и неточности вставки: разбор по углам

Разбор, не журнал. Вопрос, на который отвечает документ: почему модели ошибаются
**«по объёму»** (лимит длины ответа, переполнение контекста) и **«по точности вставки»**
(промах `Edit`, запись не в ту секцию, нестёртые плейсхолдеры) — и что не так во
взаимодействии ИИ с текстовыми задачами и флоу. Основание — `docs/model-task-matrix.md`
(все восемь задач, состояние на 2026-09-14), частоты по `docs/model-runs.md`: «лимит
длины ответа» ×34, «SEARCH/REPLACE» ×16, «сочинила/несуществующий путь» ×20, «дерево не
изменилось» ×8, «одинаков…» ×16.

Связанные документы: классы проблем матрицы и улучшения флоу по этапам —
`docs/proposals/model-flow-improvements.md` (этот документ смотрит на те же данные под
другим углом: не «что чинить по этапам», а «почему ломается само взаимодействие»);
три класса отказа A/B/C — `docs/weak-models-analysis.md`; порядок «корпус → ручки →
маршрут → веса» — `docs/model-tuning.md`; разложение этапов по колонкам
«механика/диалог/данные/модель» — `docs/stage-tooling.md`.

### Соседние классы (не объём/вставка, но та же механика)

- **Циклы и нераспознанная завершённость**: 25 ходов «начать план?» после успешного
  `FinalizeArtifact`; 40 ходов без единого `FinalizeArtifact` (форма застревания,
  детектором не покрытая); Edit↔Finalize без прогресса ×7.
- **Честность/grounding — мигрировавший фронтир**: сочинённые пути `src/loyalty.ts`,
  `test/move-hold.test.ts` ×2, `jest.expect`, `src/sender.ts` (~20 записей). Появились
  в журнале ИМЕННО после того, как `formFill`/`stepFill` сняли ошибки формы: вставку
  убрали — ошибка переехала в содержание.
- **Среда** (не путать с моделью): краши движка LM Studio, `vlm`-тег, `--gpu max`,
  `HTTP 500` ollama — помечены ⚠ и из выводов о моделях исключены.

## 2. Четыре угла: что именно не так

### Угол 1. Мышление модели (когнитивная механика)

- **Модель не планирует бюджет выхода.** Авторегрессия не имеет представления об
  оставшихся токенах; малая модель начинает «думать вслух» и обрезается на середине
  структуры. Подъём окна не лечит, потому что лечит вход, а не выход (`granite4.2-8b`).
  Reasoning-варианты подтвердили это чисто: рассуждение расходует тот же бюджет, что
  ответ. Вывод: объём выхода должен задаваться конструкцией (один узкий вопрос →
  десятки токенов ответа), а не дисциплиной модели.
- **Вставка — задача адресации, а не содержания.** `Edit` требует дословно воспроизвести
  контекст (`old_string`) — это recall байтов, на котором модели системно аппроксимируют
  (пробелы, переносы, JSDoc). «Не в ту таблицу» — та же природа: у модели нет устойчивого
  адреса секции, есть приблизительная карта документа, и похожие заголовки слипаются.
  Вывод: адрес должен быть ключом, а не цитатой (`FillField` по ключу поля, `stepFill`
  по карточке шага — оба подтверждены матрицей).
- **Мета-состояние недоступно.** «Ход завершён», «прогресса нет», «этот ответ я уже
  давал» — не свойства текста, а факты рантайма. Модель не может их увидеть в принципе;
  все успешные детекторы (`REPEAT_LIMIT`, `finalizeStreak`, `finishedByDisk`) —
  рантаймовые.
- **Ремонт без дельты бесполезен.** Модель, получившая «ошибка X» без изменённого входа,
  часто возвращает тот же ответ дословно — механизма «не повторять отказанное» у неё нет.

### Угол 2. Текст как протокол взаимодействия

- Markdown-бланк заставляет модель одновременно: понять семантику, воспроизвести
  разметку, попасть в адрес. Каждый класс ошибок матрицы ложится ровно на одну из этих
  трёх нагрузок. Убирание разметки и адресации (`formSchema` + `applyFill` + `FillField`)
  оставляет модели только семантику — и ошибки формы исчезают из журнала, а живые отказы
  становятся содержательными (сочинённые пути — про понимание, не про вставку).
- Объём входа: легенды, цитаты-шапки, разделители таблиц — `renderSheet` дал 18–30 %
  экономии без потери смысла; lean-промпты (≤5 КБ, `SKILL.lean.md`) до сих пор НЕ
  сделаны, хотя ~40 % текста скиллов — обоснования, написанные под Claude; для 8B это
  шум, вытесняющий правила.
- Плейсхолдеры-развилки `‹✅/❌/⏭›` — лишняя операция стирания, каждая такая операция —
  шанс промаха. Решение (выбор из списка, рендер рантаймом) написано, не замерено.

### Угол 3. Конструкция флоу

- Принцип «всё, что модель делает плохо, а программа умеет — делает программа» доказан
  трижды: этап 6 (конвейер рантайма — слабые модели впервые дошли до вердикта),
  `formFill` (этапы-документы), `stepFill` (3/3 шагов ×3 у `qwen3-coder-30b`,
  6/6+3/3 у 8B). Все оставшиеся красные клетки матрицы — там, где модель ещё делает
  механическое: механические поля (ветка витка ×4 у `gpt-oss-20b`), `max_tokens` руками,
  ремонт без дельты, детектор не покрывает две формы застревания.
- Вход этапа растёт по витку (intent → explore → plan …), а окно фиксировано:
  переполнение `formFill` при 70+ полях — не «модель многословна», а конструкция входа;
  истории внутри `formFill` нет, резать нечего — резать надо сами входы (проекции уже
  есть, `compactForms: 'inputs'`).
- `finishFormArtifact` может «отмыть» провал (ok:false→true при непустом diff без оценки
  качества) — известная трещина, сегодня закрытая только вердиктом этапа 6.

### Угол 4. Среда и железо

Отдельный контур, не смешивать с моделью: краши движка, `vlm`-тег, офлоад, квант
Q3_K_L (грубый квант — вероятный фактор промаха импорта у `qwen3-coder-30b-stepfill`).
Матрица уже умеет отзывать такие прогоны (⚠ среда), но классификация
`HTTP 400 terminated` как средового сбоя в провайдере не сделана — прогоны жгутся и
требуют ручной перезагрузки движка.

## 3. Корневые механизмы (синтез)

Пять механизмов порождают почти всё красное в матрице:

1. **Адресация по цитате вместо ключа** → промахи `Edit`, «не в ту таблицу», порча
   блоков. Антидот доказан: ключи полей/шагов, запись рантаймом.
2. **Бюджет выхода не задан конструкцией** → обрезки на середине структуры, reasoning
   съедает ответ. Антидот: узкий вопрос = короткий ответ; `max_tokens` считать из
   `usage.prompt_tokens`, а не ставить руками; lean-промпты.
3. **Модель пишет разметку, которую может исковеркать** → плейсхолдеры, обе ветки меню.
   Антидот написан (`formSchema`/`applyFill`/`compactForms`), НЕ замерен ни разу — это
   главный незакрытый долг измерений.
4. **Мета-состояние не видно модели** → циклы, незавершённость, дословные повторы
   ремонта. Антидот: детекторы и завершение рантаймом (два паттерна не покрыты);
   дословный повтор ремонтного ответа — детектировать и стопать (новый пункт, см. §4).
5. **Снятие ошибок формы обнажает ошибки содержания** → сочинённые пути. Антидот уже в
   строю: гейт честности `explorationPathProblem`, предусловия ask. Следующий фронтир —
   grounding, а не форма.

Главный вывод: **две оси — одно свойство в двух проекциях.** И объём, и вставка — это
«модель обязана удерживать механическое состояние (бюджет, адрес, разметку), которое
удерживает рантайм». Решение не новое — оно уже сформулировано в проекте как принцип;
этот разбор подтверждает его данными матрицы и сортирует долг.

## 4. Решение: что делать (по приоритету и цене)

Пересечение с существующими планами: `docs/proposals/model-flow-improvements.md`
§2.1/§4, `docs/stage-tooling.md` §3 (волны), `docs/model-tuning.md` §2 (ручки). Новое в
этом разборе — только пункт 4 шага 1 (дословный повтор ремонта) и сама рамка
«адресация + бюджет»; остальное — пересортировка уже размеченного.

### Шаг 0. Замерить написанное (дешевле любого кода, блокирует выводы)

1. `compactForms: 'fill'/'all'` — слой написан, не замерен НИ РАЗУ
   (`docs/model-tuning.md`, ручка №3). Серия ≥5 на `qwen3-8b` и `qwen3-coder-30b-a3b`,
   метрика — число незаполненных мест. Это прямой замер оси «вставка».
2. Датировать подтверждения `[edge]`-недобора относительно `askClaimsTopUp`
   (model-flow-improvements §4 п.0) — решает, жив ли класс.
3. Посев рецензентов (базовая линия находимости) — без неё verify-выводы слепы.

### Шаг 1. Дешёвые конструкционные правки рантайма (по одному файлу, герметичные тесты)

1. **`max_tokens` из `usage.prompt_tokens` прошлого хода** (`OpenAiCompatProvider`,
   `exec/contextBudget.ts`; `contextWindow` — общее поле `ModelDef`; у Ollama — из
   `/api/show`). Закрывает ось «объём» там, где она настройка
   (model-flow-improvements §2.1 п.2).
2. **Детектор застревания: два непокрытых паттерна** (`LoopExecutor`) — закрытие по
   диску после успешного finalize на этапах-документах; «артефакт готов, заявки нет»
   через K ходов (там же, п.1).
3. **`autofillIntent` ветки** — `SCHEMA_OVERRIDES` owner runtime + `currentBranch()`
   (там же, п.3; четыре задачи у `gpt-oss-20b`).
4. **Стоп дословного повтора ремонтного ответа в `stepFill`** (НОВОЕ, источник —
   oversize/chunk, «модель вернула тот же ответ дословно»): если ответ на ремонтный
   запрос байт-в-байт равен отклонённому, ремонт прекращается сразу, без второй
   попытки. Реализация: сравнение в `StepExecutor` до разбора блоков.
5. Классификация `HTTP 400 terminated` / сброса соединения как средового сбоя в
   `OpenAiCompatProvider` (в bench — тот же код возврата 2, что у расхождения окна) —
   матрица перестанет мерить LM Studio.

### Шаг 2. Средние (после замеров шага 0)

- Дефолт `stepFill` для локальных моделей на chunk — только серией ≥5 с контролем
  `claude-sdk:sonnet` в тот же день.
- Lean-промпты (`SKILL.lean.md` ≤5 КБ) — правка эталона методологии, решает человек.
- Волны 2–3 `stage-tooling` (`testScaffold`, стражи плана) по готовности снимков.

### Шаг 3. Дальнее

- Грамматика декодирования (`grammar` у llama.cpp / guided у vLLM) — делает невалидный
  блок `SEARCH/REPLACE` невозможным физически; актуально, если формат устоит после
  `max_tokens`.
- Корпус/QLoRA по `docs/model-tuning.md` (T1–T3) — только после корпуса и посева.

Правило замеров неизменно: одна ручка за прогон, серия ≥5, контроль
`claude-sdk:sonnet` в тот же день; результат — записью в `docs/model-runs.md` и клеткой
матрицы тем же коммитом.
