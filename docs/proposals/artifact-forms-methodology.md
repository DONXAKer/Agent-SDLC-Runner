## 1. `flow-verdict.py` и многострочные плейсхолдеры — проверено, живого бага нет

Первая гипотеза (`HOLE_RE = ‹[^›\n]*›` не видит перенос) не подтвердилась при чтении кода:
`holes_in()` (`tools/flow-verdict.py:78-97`) сканирует ПОСТРОЧНО (`text.splitlines()`,
`HOLE_RE.search(strip_literal_spans(ln))` на каждой строке отдельно) — класс `[^›\n]` в
самом регэкспе избыточен для одной строки и ни на что не влияет; реальная (не)видимость
многострочного плейсхолдера определяется построчным разбором, а не этим классом. Живой
случай из `docs/model-runs.md` (2026-09-01, поле «Подтвердил» `chunk-journal.template.md`)
уже устранён по факту — поле сейчас однострочное (`templates/chunk-journal.template.md:22`).
Оставлено записью для памяти: если многострочный плейсхолдер понадобится сознательно, у
`flow-verdict.py` для этого нет опоры (нужно склеивать продолжения строк перед разбором) —
это отдельная, более крупная правка парсера, не однострочный фикс.

## 2. `flow-verdict.py`'s `ACTION_RE` не знал `blocked_env` — применено

`tools/flow-verdict.py:40-45`: `ACTION_RE` матчил `continue|retry|escalate`, но не
`blocked_env` — притом что `verification-report.template.md`'s секция «Вердикт» и
`SDLC.md` → этап 6 («Красный из-за окружения») называют `blocked_env` как полноценное
четвёртое значение `action`, с особым правилом (не расходует попытку). Применено:
`blocked_env` добавлен в перечисление значения и в негативный просмотр (заготовка-триплет
с ним тоже теперь отклоняется).

## 3. Инлайн-повтор пары в `handoff.template.md` не выводился генерически — применено

Строка `- ‹гейт› ‹✅/❌/⏭› · ‹гейт› ‹✅/❌/⏭› — по включённым строкам набора / н/п` в
секции «Готовность» была единственным местом во всех девяти шаблонах, где ОДНА строка
несла ПОВТОР пары «гейт + статус» через `·`, без табличной структуры. Применено:
переведена в таблицу (`| Гейт | Статус |`) — та же информация, но в форме, которую схема
выводит без переопределений, и которую проще читать человеку тоже.
`flow-verdict.py` эту строку не парсил (проверено — только «**Приёмка:**» в handoff.md),
правка безопасна для эталонного гейта.

## 4. Тег `[неблокирующий]` не был показан в шаблоне `intent.template.md` — применено

`SDLC.md` и живые примеры (`example/intent.md`, вопрос 4) используют
`- [ ] **[неблокирующий]** ‹вопрос›` для вопросов, которые не блокируют старт, — но
`templates/intent.template.md`'s секция «Открытые вопросы» показывала только
`- [ ] **[блокирующий]** ‹вопрос›` и `- нет открытых вопросов`, без образца
неблокирующей строки. Применено: добавлена строка-образец с `[неблокирующий]`.

## 5. `handoff.template.md`: форма «дефектов не было» не выводится генерически

Секция «Запись о проскочившем дефекте» требует «Дефектов не было — оставить один блок со
„нет“ в поле «Имя» и `н/п` в остальных» — это условная альтернатива ЦЕЛОГО блока `### Запись
1`, а не одного поля. Схема (`deriveSchema`) не знает такой формы (`emptyAlternative` живёт
на уровне ОДНОГО поля, не группы полей) — для FillField это означает, что «дефектов не
было» модель обязана заполнить по полям вручную (имя: «нет», класс: «н/п», …), что
работает, но менее естественно, чем явная альтернатива. Предложение: не менять шаблон
(текущая форма читаема человеком), но явно принять как известное ограничение схемы —
записано здесь для памяти, если решение по FillField расширится на групповые альтернативы.

## 6. Короткие легенды и `SKILL.lean.md` для флоу `loop`

Не про формат артефактов, но про тот же класс проблемы (контекст слабой модели). Разбор
`docs/weak-models-analysis.md` (Шаг 3, не сделано): тела этапов `SKILL.md` писаны под
Claude Code, ~15–24 КБ, ~15–20 % — обоснования чисел («число взято из измерения…»). Для
сильной модели это калибровка, для слабой — шум, вытесняющий правила. Раннер уже умеет
читать альтернативное тело этапа при его наличии (маленький хук в `readSkillBody`,
предложение, не реализовано) — если эталон заведёт `SKILL.lean.md` рядом с `SKILL.md`
(правила и порядок без обоснований, цель ≤5 КБ), раннер сможет выбирать его для флоу
`loop` без правки формата остальных артефактов.

## 7. Явная форма шагов плана — легенда с образцом применена, форма НЕ сделана основной

`server/src/artifacts/planSteps.ts` уже принимает явную форму
`### Шаг N — ‹глагол + символ›` (поля `файл`, `символ`, `действие`, `закрывает`,
`проверка`, `факты человека`) как расширение к текущему шаблону — `stepFill`
(`exec/StepExecutor.ts`) использует её, когда она есть, и падает на fallback по
`files_to_touch`, когда её нет. Применено осторожно: в `templates/plan.template.md`'s
секцию «Шаги» добавлена легенда с образцом явной формы (fenced-блок) — КАК ОПЦИЯ рядом с
прежним нумерованным списком, не взамен него, чтобы не менять поведение интерактивных
сессий сильных моделей одним махом. Сделать явную форму ОСНОВНОЙ (заменить `1. ‹шаг›`
на неё) — отдельное, более смелое решение, не принято здесь.
