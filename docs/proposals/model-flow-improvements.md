# Проблемы моделей по матрице и улучшения флоу

Основание — `docs/model-task-matrix.md` (состояние на 2026-09-11). Документ собирает
основные классы проблем моделей по всей матрице, предложения по улучшению флоу для их
минимизации и отдельный разбор того, что ломает модели при написании проверки (этап
verify). Языковой срез («проверки без привязки к языку») вынесен в
`docs/proposals/language-agnostic-checks.md` — здесь он учтён как требование, но не
повторяется.

Ссылки `файл:строка` сверены с кодом 2026-09-11. Предложения, которые к этой дате уже
реализованы, вынесены в §2.0 и из списка работ убраны — иначе документ вёл бы на
сделанное.

Связанные документы: три класса отказа (A/B/C) и конструкция под слабые модели —
`docs/weak-models-analysis.md`; порядок «корпус → ручки → маршрут → веса» —
`docs/model-tuning.md`; разбор каждого прогона — `docs/model-runs.md`. Те же данные
матрицы под углом «почему ломается само взаимодействие» (объём и точность вставки как
проекции одного свойства) — `docs/proposals/volume-insertion-analysis.md`.

## 1. Основные проблемы (по частоте и системности)

### 1.1 Лимит длины ответа / переполнение контекста — отказ №1

`agents-a1-4b` и `omnicoder-9b` (по 4–5 подтверждений класса на разных задачах),
`gpt-oss-20b-f16`, `glm-4.7-flash*`, `qwen3.8-27b`. Разбор `qwen3.8-27b` с
`--stage-timeout 60` показал: уложилась в 25м53с из 60 и всё равно встала — барьер
длина ответа, не время. Для части моделей это черта генерации (многословность
независимо от размера задачи — `glm-4.7-flash`), а не настройка: снятие обрезки через
`max_tokens` помогло не всем.

Отдельный подвид: 70+ полей переполнили окно 16384 у `qwen3-8b` внутри `formFill`
(`HTTP 400 Context size exceeded`); подъём окна до 32768 снял класс, но это ручная
ручка, а не конструкция. Причина при этом **не история**: каждое поле — свежий запрос
`system + user + карточка поля` (`server/src/exec/FormFillExecutor.ts:384`), истории
между полями нет. Переполнять окно там может только сам `prompt.user` (входные артефакты
этапа растут по ходу витка). Диагноз надо снять с сырого дампа (`provider/rawLog.ts`,
`SDLC_RAW_LOG_DIR`), прежде чем лечить: скользящее окно внутри `formFill` резать нечего.

### 1.2 Краши движка — клетки меряют LM Studio, а не модель

`glm-4.7-flash-zaiorg` — детерминированный крах на конкретном поле бланка
(`HTTP 400 terminated`, движок падает целиком, нужна ручная перезагрузка);
`deepseek-r1-0528-qwen3-8b` — то же 3/3 на `intent` и на `chunk`; `gemma-4-12b`
падает на загрузке 4/4; `qwen3.8-27b` роняется с `--gpu max`. Сейчас падение движка
жжёт прогоны и требует ручного вмешательства.

### 1.3 Застревание без прогресса — детектор покрывает не все формы

`qwen3-8b` — антицикл 19→19→19 незаполненных мест; `qwen3:8b` — 3→3→3;
`qwen3-coder-30b` (ghost-requirement) — 40 ходов без единого `FinalizeArtifact`:
детектор рассчитан на серию ОТКАЗОВ финализации, а здесь её не вызывали вовсе —
форма застревания детектором не покрыта. Соседний класс — нераспознанная
завершённость хода: `qwen3-coder-30b` на ask записал ответ, `FinalizeArtifact` прошёл,
а дальше 25 ходов цикла «начать план?».

Что детектор в `server/src/exec/LoopExecutor.ts` покрывает сегодня: повтор отпечатка
вызова (`REPEAT_LIMIT`, с учётом `progressSignal`), серию отказов финализации с
неубывающим числом незаполненных мест (`finalizeStreak`, `FINALIZE_STALL_LIMIT`),
серии чтений и `Bash` без записи (`readStreak`/`bashStreak`), напоминания стража
завершения (`FINISH_REMINDERS`) и закрытие по диску при сработавшем анти-цикле
(`finishedByDisk`). Не покрыто ровно два случая выше: успешный `finalize_artifact`
возвращает текст, и цикл идёт дальше (`LoopExecutor.ts:713–722`); «правки есть,
заявки „готово“ нет» никакой серией не считается.

### 1.4 Связанность кода (этап 5) — единственный системный ЯЗЫКОВОЙ класс

`./money` вместо `./money.ts` (три модели независимо), `../tariffs` вместо
`../src/tariffs.ts`, `.js` вместо `.ts`, `ReferenceError: add is not defined`.
В `stepFill` проверка импортов после каждого шага с двумя ремонтными запросами уже
есть (`server/src/exec/StepExecutor.ts`, `REPAIRS_PER_STEP`); в свободном ходу — нет.
Расширение на другие экосистемы — `docs/proposals/language-agnostic-checks.md` §3.

### 1.5 `Edit` многострочных блоков разрушителен у слабых моделей

Три разных класса порчи за две ночи: задвоенный import (ministral3, 40 ходов),
удалённый файл с висячим импортом (gpt-oss-20b), сломанный JSDoc. `stepFill` снимает
класс по конструкции (правка блоками, не `Edit`) — это подтверждённый главный успех
стенда: 3/3 шагов ×3 у `qwen3-coder-30b`, первые полные циклы у моделей, которые в
свободном ходу давали 0 правок.

### 1.6 Недобор листа приёмки без `[edge]`

5 подтверждений на разных задачах и моделях — системный пробел, не дисперсия и не
свойство одной модели. Добор листа в `formFill` при этом существует с 2026-08-31
(`askClaimsTopUp`, `server/src/exec/FormFillExecutor.ts:443`: один повторный запрос
«добавь граничные случаи», второй — с буквальным требованием тега). Матрица не датирует
подтверждения относительно этой правки, поэтому класс не разобран: подтверждения ДО
31.08 — пункт закрыт; ПОСЛЕ — добор не срабатывает, и это дефект добора, а не пробел
формы. Различить по `bench/results/*.json` (дата прогона) — до любой правки.

### 1.7 Механические поля, отданные модели

Сверка ветки на plan у `gpt-oss-20b` — 4 задачи подряд слаг прогона вместо ветки.
Частично закрыто блоком факта (`branchFactBlock`, `server/src/run/stages/intent.ts` —
рантайм подкладывает фактическую ветку в промпт), но поле по-прежнему заполняет
модель — это прямое нарушение собственного принципа методологии «механические поля
заполняет программа». Механизм для обратного в коде уже есть: `SCHEMA_OVERRIDES` в
`server/src/artifacts/formSchema.ts` умеет объявить владельцем поля механику рантайма,
`applyFill`/`setDecision` (`artifacts/artifact.ts:645`) пишут по метке поля, а
`branchMismatchBlocker` (`Run.ts:3409`) сверяет поле с деревом и останется как был.

### 1.8 Годность не переносится между задачами

Все пять «годных по `oversize`» моделей встали на `freeship` не дальше `explore`,
включая лучшую (`gemma-4-e4b`). Вердикт «годна» по одной задаче недостоверен —
нужна серия задач, а для многоязычия — и серия экосистем (см. языковой документ §5).

### 1.9 Этап `ask` — единственный документный этап без обхода свободного хода

`intent`/`plan` умеют `formFill` (опрос по одному полю, маленький контекст на вопрос),
`explore` умеет `exploreFill` (конвейер закрытых вопросов рантайма с заземлением по
индексу). У `ask` — ни то, ни другое: `stageModule('ask').formFillExecutor === false`
намеренно, не пробел. Причина — архитектурная, не «руки не дошли»: `FormFillExecutor`
опрашивает поле прямым completion'ом без цикла tool-use и физически не может позвать
`AskHuman`, а весь смысл этапа 3 — задать человеку открытый вопрос. Живой инцидент,
задокументированный тестом (`server/test/stageTurns.test.ts`, «formFill не покрывает
ask»): на витке `ministral-8b` без цикла tool-use модель тихо ПРИДУМАЛА себе ответ
(«пропущено») вместо того, чтобы спросить — все три human-кейса скрытых тестов
покраснели по конструкции, не по вине модели.

Повторно проверено 2026-09-16 (серия `polza-mixed`, `docs/model-error-taxonomy.md`):
попытка включить `formFillExecutor: true` для `ask` (по прямой аналогии с `plan`, та же
структура модуля, схема бланка `clarification-report.template.md` уже покрыта
`SCHEMA_OVERRIDES`) сразу упала на регрессионном тесте выше — типобезопасность и
структурное сходство с `plan.ts` не гарантируют архитектурной совместимости, когда у
этапа есть требование к самому МЕХАНИЗМУ хода (цикл tool-use), а не только к форме
артефакта. Правка отклонена, откачена без остатка.

Практическое следствие: `ask` у моделей с тесным окном контекста (например,
`polza:qwen3-14b`, `contextWindow: 34000`) остаётся единственным узким местом связки,
не закрываемым существующими ручками — только тюнингом `contextWindow`/
`historyBudgetBytes` с неоднозначным эффектом (см. `docs/model-error-taxonomy.md`,
класс «ask без обхода formFill»).

## 2. Как улучшить флоу (по приоритету)

Принцип тот же, что уже сработал на этапе 6 и `formFill`: всё, что модель делает
плохо, а программа умеет, делает программа; модели остаётся один узкий вопрос с
узким контекстом.

### 2.0 Уже сделано — в список работ не входит

- **План как контракт.** Пустой `files_to_touch` блокирует старт chunk
  (`server/src/run/Run.ts:2786`); числа плана, не встречающиеся в diff'е
  (`SIDE_SURCHARGE_PCT` у `gemma-4-e4b`), сверяются `run/planConstants.ts`
  (`Run.ts:3119`).
- **Связанность после шага** — в `stepFill` (§1.4). Пер-экосистемное расширение —
  языковой документ §3.
- **Скользящее окно истории** во флоу `loop` — `server/src/exec/history.ts`
  (`trimHistory`, `HISTORY_KEEP_LAST`). Сверка заявленного окна с фактически
  загруженным у LM Studio — `provider/lmstudioContext.ts` (`ModelDef.contextWindow`).
- **Таблица гейтов в verify** заполняется рантаймом (`verifyAutofill`), не моделью.
- **Добор `[edge]`** в `formFill` — `askClaimsTopUp` (§1.6; работает ли — не разобрано).
- **`max_tokens` по остатку окна** (бывший п. 2 §2.1). `exec/contextBudget.ts` — у
  `FormFillExecutor` (все пять мест запроса, `contextWindow` маршрута из `Run`),
  `StepExecutor`, `ExploreExecutor`, `LoopExecutor` (по `prompt_tokens` прошлого хода).
  Оценка считает байты UTF-8, а не `.length`: кириллица занижала вдвое. Окно Ollama
  читается из модфайла (`provider/ollamaContext.ts`); ручные `params.max_tokens` из
  `config/models.json` убраны. Первый ход `LoopExecutor` (числа от сервера ещё нет) — по
  оценке исходящего запроса со схемами инструментов.
- **Ветка витка пишется рантаймом** (бывший п. 3) — `stages/intent.ts::autofillBranchField`.
- **Механические поля модели не отдаются** (§1.7, шире ветки). Название, «Вход» и «База»
  плана, даты прогонов готовности, названия отчётов 2–3 заполняет `run/formAutofill.ts` до
  модели; `FormFillExecutor.modelGroupFields` исключает поля рантайма из вопросов только у
  шаблонов, которые автозаполнение закрывает целиком (скрепа по реальным шаблонам —
  `formAutofill.test.ts`). Журнал chunk'а и handoff — вне набора: там закрыть поле некому.
- **Падение движка классифицируется как средовой сбой** (бывший п. 4, часть
  «классификация»): `terminated`/`fetch failed` → `ProviderEnvError`
  (`ENGINE_UNAVAILABLE_SUBSTRINGS`, `provider/ChatProvider.ts`). Прогрев и
  автоперезагрузка не сделаны.
- **Детектор застревания, соседние формы** (часть п. 1): спасение текста при
  `finishReason === 'max_tokens'` и одно напоминание при 60% бюджета ходов без принятой
  правки (`LoopExecutor`). Буквальные паттерны п. 1 не закрыты.

### 2.1 Что делать

Номера пунктов — прежние: на них ссылается §4, сделанные пункты перенесены в §2.0.

- **п. 1. Детектор застревания — два непокрытых паттерна** (§1.3), оба в `LoopExecutor`:
   - *финализация прошла, модель продолжает*: на этапах-документах после успешного
     `finalize_artifact` при `finishGuard() === null` этап закрывает рантайм — тот же
     `finishedByDisk`, но проактивно, а не только при сработавшем анти-цикле. На chunk
     не применять: журнал может быть готов раньше кода;
   - *правки есть, заявки нет*: симметрично `readStreak`/`bashStreak` — после хода с
     записью, если `finishGuard()` уже молчит, одно напоминание «артефакт готов — зови
     `FinalizeArtifact`», через K ходов — закрытие по диску. Считается не «N ходов», а
     «готов по диску, а заявки нет».
- **п. 4. Обвязка движка — прогрев и автоперезагрузка** (§1.2, остаток; классификация
  сделана). Прогрев одним запросом — в преполёте bench. Автоперезагрузка (`lms load`) —
  только за явным флагом оператора: GPU общий.
- **п. 5. `stepFill` — дефолт для локальных моделей на chunk.** Правка не кода, а
  `config/models.json`, и только после серии ≥5 с контролем сильной модели в тот же
  день — «одна ручка за прогон» важнее скорости.
- **п. 6. Годность по двум фикстурам** (§1.8) — правило заполнения матрицы, не код:
  клетка «годна» только когда `oversize` и `freeship` дошли до одного этапа; иначе —
  «годна на oversize».
- **п. 7. `ask` без обхода formFill** (§1.9) — новый исполнитель для `ask` отклонён
  (архитектурно несовместим, живой инцидент, тест защищает). Дешёвая, ещё НЕ
  проверенная живьём альтернатива уже в коде: `compactForms: 'inputs'`
  (`prompt/build.ts::renderSheet`) сжимает входные артефакты `ask` (`intent.md` +
  отчёт разведки) до компактной проекции без потери содержимого — легенды/цитаты вместо
  полного текста таблиц. Живой замер `polza-mixed` (2026-09-16) показал: базовый промпт
  `ask` (система+пользователь, ДО единого вызова инструмента) уже занимал ~24 КБ на
  задаче `freeship` — именно та часть, которую `compactForms: 'inputs'` призван сжать, и
  именно она, а не накопленная история хода, оказалась основным вкладом в переполнение
  окна. `docs/model-runs.md` → «Состояние»: слой покрыт 1130+ герметичными тестами, но
  серии на реальных моделях (правило «серия ≥3, контроль на сильной модели») не было.
  Следующий шаг — не новый код, а замер: включить `compactForms: 'inputs'` (или `'all'`)
  моделям с тесным окном на `ask` и сравнить базовый промпт до/после.

## 3. Что ломает модели при написании проверки (этап verify)

Отдельный букет матрицы, худший по инструментированности:

| Класс | Пример из матрицы | Что есть в коде | Лекарство |
|---|---|---|---|
| Проверка зеленеет, не проверяя код | `gpt-oss-20b`: `NaN == NaN` зеленеет, эскалация по своим тестам | посев построен (`bench/src/seeds.ts`), базовая линия снята по 2 классам из 9 | посев как калибровка проверки — серии по остальным классам |
| «Зелёный, потому что не запустился» | общий вид: 0 собранных тестов = exit 0 у многих раннеров | `testOne` ставит `✅` по одному `exitCode === 0` (`gates/builtin/index.ts:659`) | разбор счётчика вывода по экосистеме (`# tests N` у `node:test`, `collected 0 items` у pytest, …) → `⏭ «тесты не собраны»` без `envBlocked`; где формат неизвестен — код возврата плюс строка об этом |
| Собственный тест ломается чаще продукта | `qwen3-coder-30b` ×3, `qwen3:8b` ×2 (`add is not defined`) | тест модели гоняется тем же гейтом «Тесты», отдельно не различается | различать по diff'у: падают ТОЛЬКО тестовые файлы из патча при зелёном остальном → класс «проверка плоха» в `verdict/classify.ts`; требует, чтобы гейт отдавал имена упавших файлов — пер-экосистемно |
| Регрессия между попытками | `ministral-14b` затёрла экспорт, добавленный ею же | `VerdictInput.regressions` наполняется только из текста рецензента (`verdict/collect.ts:425`) | считать механически: `claim-N` был `✅` в попытке K−1 и стал `❌` в K → в то же поле, без нового условия вердикта |
| Адресация находок врёт | «файл:строка 154», фактически `:158` | `anchorFound` (`run/verifyReport.ts:238`) знает, что цитата не нашлась; запись уходит «отдельной строкой» | чинить, а не отклонять: если цитата есть — рантайм ищет её в патче и сам переписывает номер строки; «без привязки» остаётся только запись без цитаты |
| Эскалация по своим тестам, а не по коду | `gpt-oss-20b`, verify | `decideAction` различает только счётчик и `noProgress` | вход от строки «собственный тест» выше → классификатор (`docs/backlog/red-cause-classifier.md`) |
| Поле решения не заполнено | `qwen3-8b` (lmstudio): `blocked`/`retry` обе ветки | таблицу гейтов рисует рантайм (`verifyAutofill`); незаполненным было поле-развилка | стирание лишней ветки меню — `applyFill` при `compactForms: 'fill'` (не замерено) |
| effort-high не укладывается | `gpt-oss-20b` reviewFill: таймаут 30 мин ×9 | капа нет | кап по времени/числу хунков на `reviewFill`; при превышении — остаток на свободный ход, не таймаут этапа |

Все лекарства нейтральны к языку — подробности и обоснование (посев вместо
невозможного линтера «тест ничего не проверяет») в языковом документе §4.

## 4. Порядок работ

0. Перед правками — два разбора по данным, не по коду: датировать подтверждения
   §1.6 относительно `askClaimsTopUp` и снять причину переполнения в `formFill` (§1.1)
   с сырого дампа. Оба меняют список работ.
1. Посев: снять базовую линию находимости рецензентов по остальным классам — мерило
