# Ансамбль рецензентов на verify

**Пункт плана:** 9 · **Категория:** качество за меньше итераций
**Слаг витка:** verify-reviewer-ensemble

## Зачем

Сегодня на этап назначается ровно одна модель: `ResolvedProfile.routes` —
`Record<StageId, ResolvedRoute>` (`server/src/config/schema.ts`), и `resolveProfile`
(`server/src/config/profiles.ts`) кладёт туда один маршрут на этап. Соответственно этап 6
идёт одним прогоном одной модели, а `Run.runStage` (`server/src/run/Run.ts`) пишет ровно
один отчёт — `paths.verificationReport(chunk, attempt)`.

Из этого следует практическая слабость: пропуск единственного рецензента ничем не
компенсируется. Гейт «Ревью независимым агентом» зажигается по факту одного состоявшегося
вызова субагента (`Run.markReviewerRan`, реестр `REVIEWER_AGENTS`), то есть «ревью было» —
но насколько оно въедливое, зависит от одной модели и одного сэмпла. Два-три независимых
рецензента на разных моделях дают несколько независимых шансов найти расхождение до того,
как виток уйдёт в handoff, — а находка на этапе 6 дешевле, чем дефект, найденный после
коммита.

Важно: агрегация «худший статус побеждает» уже реализована — `worst()` в
`server/src/verdict/collect.ts` сводит статус прогона и статус отчёта. Ансамбль — это
третий и четвёртый источник того же вида, а не новое правило вердикта.

## Что сделать

1. Расширить `ProfileDef.stages` (`server/src/config/schema.ts`) так, чтобы значением был
   либо id модели, либо массив id. Форма конфига `config/projects/*.json` при этом должна
   остаться обратно совместимой: строка = список из одного.
2. Ввести в `ResolvedProfile` поле, где у этапа лежит список маршрутов
   (`Record<StageId, ResolvedRoute[]>`), а `routes[stage]` оставить первым/основным
   маршрутом — от него зависят `Run.executorFor` и `stage_started`; переписывать всех
   потребителей разом не нужно.
3. `checkReviewerRule` (`server/src/config/profiles.ts`) переписать на списки: правило
   «verify строго сильнее chunk» должно требовать, чтобы **минимальный** rank среди
   маршрутов verify был строго больше **максимального** rank среди маршрутов chunk. Иначе
   ансамбль становится способом протащить слабого рецензента рядом с сильным.
4. В `Run.runStage` для `stage === 'verify'` прогнать исполнителей по всем маршрутам этапа
   и получить N отчётов. Имена файлов — новые, в `server/src/artifacts/paths.ts`
   (`verificationReport` сегодня знает только chunk и attempt; нужен третий ключ —
   индекс рецензента). Короткие ключи артефактов из `artifactPathOf` расширить тем же
   образом, иначе оператор не сможет подписать решение по конкретному отчёту.
5. Агрегация: `Run.computeStageVerdict` вызывает `collectVerdictInput` по каждому отчёту и
   сводит полученные `VerdictInput` в один — статусы гейтов через уже существующий `worst`,
   пункты приёмки по тому же принципу (`❌` > `⚠` > `✅`), `confirmedReviewFindings` —
   сумма, списочные поля — объединение. `computeVerdict` при этом не меняется вовсе: она
   остаётся чистой функцией по одному входу.
6. Стоимость: каждый дополнительный рецензент — это полный прогон этапа 6. Бюджет
   (`project.maxBudgetUsd`, `ExecRequest.maxBudgetUsd`) делится между ними, а не выдаётся
   каждому целиком.

## Риски и инварианты

- **Правило рецензента — не декорация.** Самый вероятный способ сломать задачу — свести
  сравнение рангов к «хотя бы один сильнее». Тогда ансамбль становится легальным способом
  протащить дешёвую модель в этап 6.
- **Вердикт не спрашивает модель.** Сведение N отчётов — код и чистая функция; ни один
  шаг агрегации не должен превращаться в вопрос «а вы согласны?» к какой-либо модели.
- **Ложный зелёный.** Агрегация обязана быть по худшему. Любая формула вида «большинство»
  или «среднее» открывает ровно тот путь, который закрывали `worst()` и
  `evidenceProblem()`: два слабых рецензента перекрывают одного сильного.
- **`runtimeAuthoritativeWhenGreen`.** Исключение для гейта ревью считается по факту вызова
  субагента; при N рецензентах факт «рецензент отработал» должен означать, что отработали
  **все** объявленные, а не любой один — иначе гейт минимума зеленеет от частичного прогона.
- Стоимость витка растёт кратно числу рецензентов — это надо показать оператору до старта,
  а не после списания бюджета.
