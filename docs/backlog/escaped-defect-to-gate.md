# Проскочивший дефект → предложение гейта

**Пункт плана:** 21 · **Категория:** наблюдаемость
**Слаг витка:** escaped-defect-to-gate

## Зачем

Phase 4 скилла `sdlc-handoff` требует на каждый проскочивший дефект одно решение из трёх:
**конструкция**, **проверка** (новый гейт или парная проверка обхода — дописывается в
`.sdlc/gates.md`) или **принятый риск** (строка долга с именем и датой). Решение
принимается вместе с человеком.

Рантайм в этом месте сегодня не участвует ничем. Он умеет разбирать `.sdlc/gates.md`
(`server/src/gates/gatesFile.ts`: строки набора, таблица «Долг», `openDebt`,
`configProblems`) и знает, какие проверки у него встроены (`BUILTIN` в
`server/src/gates/builtin/index.ts`: сборка, тесты, scope, анти-обход, секреты в diff,
предусловия публикации). Но при выборе «проверка» человек и модель пишут строку набора
с нуля, ничем не сверяясь — и промахиваются ровно в тех местах, которые уже стоили
дефектов в этом коде: имя строки не совпадает с ключом встроенной реализации
(`gateKey`), колонка «Где отчитывается» не распознаётся и гейт молча не участвует в
вердикте, колонка «Чем реализован» содержит прозу с именем в кавычках и рантайм пытается
исполнить `files_to_touch` как команду.

То есть петля качества сейчас разомкнута в самом узком месте: запись о дефекте есть, а
проверка, которая его бы поймала, не появляется — или появляется нерабочей.

## Что сделать

1. Дать этапу 7 машинную подсказку по варианту «проверка»: готовую строку набора в форме
   `| Имя | да | этап 6 | \`команда\` |` с уже подставленными значениями, которые
   рантайм умеет исполнить.
2. Собирать подсказку из того, что известно коду: список имён `BUILTIN` (для них команда
   не нужна — сработает встроенная реализация), уже присутствующие строки набора (чтобы
   не предложить дубль имени — две строки с одним именем `configProblems` считает
   дефектом набора), допустимые значения «Где отчитывается» из `ReportsAt`.
3. Прогонять предложенную строку через `parseGates` + `configProblems` **до** того, как
   она попадёт человеку: предложение, которое не проходит собственный разбор рантайма, —
   не предложение.
4. Для варианта «принятый риск» так же готовить строку долга с полями, которые
   `parseGates` считает закрывающими: «проверяет руками» либо «риск принят», плюс имя и
   дата, проходящие `signatureProblem`.
5. Ничего не записывать в `.sdlc/gates.md` за человека. Выбор из трёх — его, скилл
   требует спрашивать через `AskUserQuestion` и не предлагать готовое решение как
   принятое. Рантайм готовит текст, человек решает.
6. Отдельным пунктом — вариант «посев»: класс дефекта, для которого предлагается новый
   гейт, естественно ложится в `sdlc-seed` (калибровка посевом, «вне витка»). Здесь
   достаточно назвать это как рекомендацию с именем класса, а не реализовывать посев.

- `server/src/run/Run.ts` — подача подсказки этапу `handoff` через `extra`

## Приёмочный лист

- [ ] Предложенная строка набора после вставки в `.sdlc/gates.md` разбирается
      `parseGates` и не добавляет ни одной проблемы в `configProblems`
- [ ] Имя предложенного гейта не совпадает по `gateKey` ни с одной существующей строкой
- [ ] Если имя есть в `BUILTIN`, предложение не выдумывает команду
- [ ] Предложенная строка долга считается закрытой (`DebtRow.closed === true`) при
      подстановке реального имени и даты
- [ ] Ни один путь кода не пишет в `.sdlc/gates.md` без решения человека
- [ ] Текст, показанный человеку, не утверждает, что гейт «добавлен» — только «предложен»

## Риски и инварианты

- `.sdlc/gates.md` — конфигурация рантайма. Автоматическая правка набора агентом ломает
  принцип «агент, который может переписать одобренный план, может снять с себя любое
  ограничение»: на этапе 7 `gates.md` намеренно выведен из `protectedArtifacts` только
  ради строки долга (см. `server/src/run/stages.ts`), и расширять это до автоматического
  добавления гейтов нельзя.
- `\b` в регулярках не работает по кириллице — любая новая проверка формата строки
  перечисляет окончания явно, как `parseEnabled`/`parseCommand`.
- Ошибка в предложении дороже отсутствия предложения: гейт, который выглядит включённым,
  но не прогоняется, — это ложный зелёный, ровно то, против чего построен вердикт.
