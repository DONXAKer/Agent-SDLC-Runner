# Гейт идиоматичности на линтере экосистемы

**Пункт плана:** 4 · **Категория:** мультиязычность и паттерны
**Слаг витка:** lint-gate-presets

## Зачем
«Пиши идиоматично для языка» сегодня существует только как текст этапа в `SKILL.md`
эталона, попадающий в промпт через `readSkillBody` (`server/src/prompt/build.ts:39`). Это
надежда: слабая локальная модель её не исполняет, а проверить некому — среди встроенных
реализаций (`BUILTIN` в `server/src/gates/builtin/index.ts:495`) линтера нет вовсе, там
шесть имён: сборка, тесты, scope, анти-обход, секреты, предусловия публикации.

Механика для проверки уже есть и работает: строка `.sdlc/gates.md` с командой в обратных
кавычках исполняется рантаймом (`parseCommand`, `server/src/gates/gatesFile.ts:101` →
`runOne`, `server/src/gates/run.ts:56`). То есть проект уже сегодня может написать
`` `ruff check .` `` и получить гейт. Не хватает двух вещей: встроенной реализации под
общим именем (чтобы имя строки набора было стабильным и попадало в вердикт), и выбора
линтера по экосистеме вместо ручного вписывания команды в каждый проект.

Смысл витка — перенести «паттерны языка» из промпта (надежда) в гейт (проверка).

## Что сделать
1. Добавить в описание экосистемы команду линта: ruff (`ruff check`) и mypy для Python,
   `golangci-lint run`, `cargo clippy -- -D warnings`, ESLint для JS/TS, `ktlint`/`detekt`
   для Kotlin — там, где инструмент общепринят.
2. Завести встроенный гейт под именем строки набора (например «Линт экосистемы») и
   зарегистрировать его в `BUILTIN`. Ключ — через `gateKey`, как у остальных.
3. Отличать три исхода честно: линтер не установлен → `⏭` со словами «линтер не найден,
   идиоматичность НЕ проверялась»; линтер отработал с нарушениями → `❌` с хвостом вывода;
   чисто → `✅`. `⏭` роняет вердикт, пока человек не подпишет неприменимость, — это и есть
   нужное поведение, а не досадный побочный эффект.
4. Ограничить проверку изменёнными файлами, где линтер это умеет (ruff, eslint принимают
   пути): гейт на всём репозитории краснеет от чужого долга и обучает игнорировать себя.
   Где инструмент работает только по модулю (clippy, golangci-lint) — так и сказать в
   выводе.
5. Дать проекту переопределение — через профиль (`project-language-profile`) и через строку
   набора; приоритет тот же: набор > профиль > пресет.
6. Описать строку в шаблоне набора гейтов методологии — с честным «Где отчитывается: этап
   6», иначе `configProblems` (`gatesFile.ts:222`) справедливо назовёт её молчаливо
   отключённой.

## Файлы

- `server/src/gates/builtin/index.ts` — новый `lintGate` и строка в `BUILTIN`

## Приёмочный лист
- [ ] Строка набора «Линт экосистемы» без команды в обратных кавычках попадает во встроенную реализацию (а не в `⏭` «исполнить нечем» из `run.ts:79`).
- [ ] Отсутствующий линтер даёт `⏭` с текстом, из которого видно, что проверка не состоялась; `✅` в этом случае невозможен.
- [ ] Найденные нарушения дают `❌` и последнюю содержательную строку вывода линтера.
- [ ] Команда из `.sdlc/gates.md` перекрывает пресет — проверяется тестом на `runOne`.
- [ ] Гейт не является строкой обязательного минимума: `MINIMUM` в `gatesFile.ts` не тронут, и выключенный линт закрывается строкой долга по общим правилам.

## Риски и инварианты
- Команда линтера идёт через `runShell` → `checkBash`: `DenyList` — нижняя граница, и конфигом она не ослабляется. Команда с `--fix` (ruff, eslint, clippy) недопустима по смыслу: гейт проверяет, а не правит рабочее дерево — молчаливая правка испортит diff, который перегенерирует этап 6, и обойдёт одобрение записи.
- Гейт, краснеющий от накопленного долга проекта, обесценивает все гейты. Ограничение изменёнными файлами здесь не оптимизация, а условие полезности.
- Не превращать линт в обязательный минимум без решения человека: пятёрка `MINIMUM` — это конфигурация процесса, её расширение меняет условие старта витка для всех проектов.
