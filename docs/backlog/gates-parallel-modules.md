# Параллельные build/test по модулям monorepo

**Пункт плана:** 7 · **Категория:** мультиязычность и паттерны
**Слаг витка:** gates-parallel-modules

## Зачем
`resolveModule` (`server/src/gates/builtin/index.ts:69`) возвращает **один** каталог:
`moduleDirFromPlan` (`server/src/gates/builtin/logic.ts:96`) идёт от первого файла
`files_to_touch` вверх до первого каталога с манифестом и на этом останавливается. Оба
обязательных гейта — `buildGate` (строка 220) и `testGate` (строка 258) — работают в этом
единственном каталоге.

В моно-репо это даёт ложный зелёный по построению: план трогает `server/` и `web/`, гейт
собирает `server/`, `web/` не проверяется, а отчёт этапа 6 пишет «Сборка ✅». Комментарий у
`moduleDirFromPlan` фиксирует предыдущую версию той же болезни (алфавитный перебор брал
`frontend/`, тогда как правки шли в `vscode-extension/`) — лечение было правильным, но
неполным: случайный модуль заменили на первый, а не на все затронутые.

Ровно этот же разрыв виден в scope-гейте: `scopeViolations` уже помечает `sameName`-промах
модулем, то есть кодовая база знает, что план может смотреть в несколько мест.

## Что сделать
1. Заменить `moduleDirFromPlan` на функцию, возвращающую **множество** каталогов-модулей:
   для каждого пути из `planFiles` подняться до ближайшего манифеста, собрать уникальные
   каталоги, сохранить порядок первого появления. Прежнюю функцию оставить только если у
   неё найдутся другие вызывающие (проверить grep'ом).
2. `resolveModule` в `builtin/index.ts` перевести на список; `buildGate` и `testGate`
   прогоняют команду по каждому модулю.
3. Агрегировать статусы по правилу «худший побеждает»: любой `❌` → `❌`; иначе любой `⏭` →
   `⏭`; `✅` только если проверены все. Это то же правило, по которому вердикт берёт худший
   из двух статусов (`server/src/verdict/verdict.ts`) — второй его копии в кодовой базе быть
   не должно, вынести/переиспользовать.
4. В `lastLine` перечислять модули с их исходами: строка «Сборка ❌» без имени модуля в
   моно-репо не диагностична.
5. Параллелить существующим `inBatches` (`builtin/index.ts:123`) с малым размером пачки, а
   не новым пулом.
6. Отдельно решить и записать, что делать с общим деревом: комментарий `runGates`
   (`server/src/gates/run.ts:95-99`) прямо объясняет, почему гейты идут последовательно —
   они делят рабочее дерево, git-индекс и память. Параллельные `build`/`test` разных модулей
   этот довод не отменяют: gradle-демон и `npm ci` конкурируют за диск и память, а тесты
   могут делить порт или БД. Значение по умолчанию — последовательный проход, параллельность
   включается лимитом в конфиге и оправдывается замером.

## Файлы
- `server/src/gates/builtin/logic.ts` — `moduleDirsFromPlan` вместо/поверх `moduleDirFromPlan`
- `server/src/gates/builtin/index.ts` — `resolveModule` отдаёт список; `buildGate`/`testGate` идут по модулям и агрегируют
- `server/src/gates/run.ts` — потолок времени: `timeoutMs` сегодня трактуется как «на гейт», при N модулях это N таймаутов
- `server/test/gates.test.ts` — план с двумя модулями, агрегация статусов

## Приёмочный лист
- [ ] План, трогающий два модуля с разными манифестами, приводит к двум прогонам сборки и двум прогонам тестов.
- [ ] Падение любого модуля даёт `❌` всего гейта; `✅` невозможен, пока хоть один модуль не проверен (`⏭`).
- [ ] `lastLine` называет модуль, на котором получен исход.
- [ ] Правило «худший статус» существует в кодовой базе в одном месте — проверяется grep'ом.
- [ ] Общий бюджет времени гейта не растёт линейно с числом модулей молча: либо `timeoutMs` делится, либо в конфиге появился явный потолок, и в `⏭` по таймауту сказано, чего именно не хватило.
- [ ] План из одного модуля даёт ровно сегодняшнее поведение и ту же строку результата.

## Риски и инварианты
- Каждому включённому гейту «этап 6» соответствует **ровно одна** строка результата с именем дословно как в наборе (шапка `server/src/gates/run.ts`). Разбивать по модулям на несколько `GateRunResult` нельзя: сверка отчёта с набором идёт по именам, и лишняя строка ломает и сверку, и вердикт.
- Ложный зелёный — главный класс дефекта этого проекта. Агрегация обязана быть пессимистичной.
- Параллельность на общем дереве — тот самый «мнимый выигрыш при настоящих взаимных помехах», о котором говорит `runGates`. Включать по умолчанию нельзя.
- `resolveModule` также кормит проверку установленных зависимостей — она становится помодульной.
