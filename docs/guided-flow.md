# Guided flow

Экспериментальный режим для небольших задач одной локальной модели. Он использует
структурированную проработку v3. [Методология: PDSA и poka-yoke](../server/methodology/guided.md).
Существующие задачи автоматически не переводятся в guided.

## Запуск

В новой задаче на этапе intent выбрать guided. Все маршруты профиля, включая ревью,
должны указывать на одну модель с локальным endpoint. API: при первом запуске intent
передать `executionMode: "guided", preparationVersion: 3`. Дальше режим закреплён
за задачей. GET задачи возвращает `executionMode` и `guided` со временем, группами,
наблюдениями и причиной остановки. Тексты снимков для отката в API не возвращаются.

Пример стенда (таймауты CLI задаются **в минутах**):

```powershell
node bench/src/cli.ts --all --task freeship --model ollama:qwen3-8b-ctx32k-stepfill-compactfill --execution-mode guided --stage-timeout 30 --run-timeout 30
```

План сравнительной матрицы без вызовов моделей:

```powershell
node bench/run-guided-matrix.mjs --pilot
```

Добавить `--run` для последовательного выполнения 72 прогонов. `--extended --run` —
480 прогонов: 6 моделей × 8 задач × 5 повторов × 2 режима. Manifest содержит порядок,
отпечаток исходников и результаты; при изменении исходников серия останавливается.
Каждая пара использует v3, одну модель, строгий банк ответов. Неизвестные вопросы
не получают выдуманный ответ. Предполёт остаётся включён. Технические сбои сохраняются.
Стенд ограничивает и полное время 30 минутами; это строже runtime-бюджета, который
исключает ожидание человека. Для автоматического банка ответы приходят сразу.

## Устройство

| Компонент | Ответственность |
|---|---|
| `GuidedExploreExecutor` | JSON-ответ о конкретном исходнике; путь закрепляет рантайм, отчёт с четырьмя колонками собирается механически |
| `GuidedAskExecutor` | Сначала ответ по источнику с проверкой дословной цитаты; затем доставка недостающих бизнес-вопросов. Ответы человека и выводы модели хранятся отдельно |
| `GuidedPlanExecutor` | Связный JSON-план: действие, файл, символ, проверка и зависимости вместе; Markdown собирает рантайм |
| `guidedState` | Группировка зависимостей, редакции, время, сохранение состояния и свидетельства существующего кода |
| `GuidedExecutor` | Ограниченный JSON-протокол patch/read/search/question/no_change/split, транзакция группы, проверки, восстановление |
| `guidedExecutor` | Привязка к согласованной проработке и зарегистрированным гейтам проекта |
| `Run` | Выбор исполнителя, одна модель, бюджет времени, операторские разрешения и финальная приёмка |
| `reviewFill` / `claimFill` | Проверка фактического diff либо свежих исходников для задачи без изменений |
| `guidedVerification` / `guidedHandoff` | Отчёты из структурированных суждений и точных runtime-фактов; подписи человека не генерируются |

В `.sdlc/<slug>/.runner/guided.json` хранятся группы, прогнозы, наблюдения, время и
незавершённая транзакция. Рантайм пишет состояние; модель не имеет права его изменять.
Перед записью все предложения проверяются на область, хэш и уникальность SEARCH,
после чего запрашиваются разрешения для всей группы. Гейты запускаются после группы.
Несколько файлов не образуют атомарную операцию файловой системы: журнал позволяет
восстановить собственные версии после сбоя. Внешняя правка вызывает конфликт и сохраняется.

Ревью выполняет та же модель отдельным запросом. Это не независимая компетенция;
коррелированные ошибки должны ловиться проверками и удержанными задачами.
Intent использует существующее заполнение структурированных требований. Качество
извлечения требований и суждений модели по-прежнему ограничивает результат.

## Прогноз для задач

| Задача | Ожидаемое поведение | Что ещё может помешать |
|---|---|---|
| freeship | Извлечь заданные границы веса, уточнить правило silver при необходимости, менять тариф и новый тест одной группой | Потеря ограничения на старые тесты и лишние вопросы — уже наблюдались |
| config-default | Найти источник конфигурации и проверить явное значение и default | Модель может заменить конфигурацию константой; нужны скрытые тесты |
| two-right-answers | Следовать подтверждённому контракту владения и копирования | Коррелированная ошибка реализации и саморевью |
| wrong-diagnosis | Проверить диагноз по коду, менять доказанную причину | Исследование может принять предположение пользователя за факт |
| multi-file-cascade | Объединить контракт, потребителей и тесты до проверки | Большая группа может не поместиться в контекст |
| zero-change-verify | Реализовать требования задачи ledger и проверить изменения; название задачи не означает запрет записи | Заявление no_change само по себе ничего не доказывает |
| scope-bait / security-bait | Блокировать запрещённые пути, проверить содержимое допустимых правок | Семантический дефект внутри разрешённого файла требует проверок |

Это проверяемые гипотезы. Рантайм надёжнее контролирует область и доказательства,
но не превращает слабое понимание задачи в правильное решение автоматически.

## Исправления после быстрого прогона 2026-10-04

- Ask классифицирует каждый кандидат: ответ по источнику, обратимое инженерное решение,
  запрос контекста, существенный бизнес-вопрос или техническая ошибка протокола.
  Комментарии, названия новых тестов и способ проверки выбираются автоматически в пределах требований.
- Журнал в preparation.json сохраняется после каждого решения. Ответы человека,
  выводы модели и инженерные решения имеют отдельные разделы отчёта. При изменении
  требований или процитированного исходника решение требует повторной проверки.
- Ошибка JSON или недостоверная цитата дают техническую остановку; они не становятся
  запросом отсутствующего бизнес-правила. Старые выводы без хешей сохраняются как
  исторические основания и перепроверяются.
- Plan сохраняет сырой ответ, разобранный кандидат, нормализованный документ и ошибку.
  После успешного разбора модель исправляет отдельные карточки; новым карточкам ID
  назначает runtime. Обязательный путь нового теста передаётся до первого ответа.
- Генератор тестовой карточки сохраняет содержательную проверку и контракт и не
  добавляет терминологию конкретной предметной задачи в другие задачи.

Проверки: 78 тестов guided/preparation/intentImplementationPaths и отдельный тест маршрута
независимого ревью. Это проверка механизмов, не доказательство успешного прохождения моделью.
Быстрая проба: `node bench/run-guided-sample.mjs --quick` — Granite на add-validator
и zero-change-verify, с общим отпечатком исходников и регистрацией всех остановок.
Расширение до пяти моделей зависит от подтверждённого сквозного результата.

Проба `guided-sample-20261004090552666`: обе задачи дошли до Plan без вопросов
человеку, но обе остановились до Chunk (0/2). add-validator — отсутствующая карточка
при ремонте; zero-change-verify — неизвестная/неоднозначная карточка. Это не успех.
После пробы runtime-карточки включены в общий кандидат с их ID; успешная частичная
правка сохраняется даже при незаполненной соседней карточке. Ремонт получил отдельную
короткую подсказку без полной схемы плана; схема ограничивает допустимые claim-ID,
ID карточек и размер текстовых полей. Перепроверка барьера Plan:
`node bench/run-guided-sample.mjs --plan-smoke` (одна задача, 8 минут на запуск,
остановка после Plan). Даже успешный Plan в этой пробе не считается полным успехом.

Проба `guided-sample-20261004093124793`: Plan снова отклонён (3 мин 17 с,
5 ответов вместо 6 мин 23 с в первой пробе), сквозной успех не измерялся.
Модель заменяла существующую карточку новой с id=0 и оставляла claims пустым.
Доработка: однозначный существующий путь восстанавливает ID карточки; новые ID
назначаются только новым путям. Каждый шаг требует хотя бы один допустимый claim
в JSON-схеме. Первичное адресное замечание сохраняется при ошибке протокола ремонта.
Дополнительное чтение исходника на Ask теперь попадает в общий журнал доказательств.

Проба `guided-sample-20261004093924313`: Plan отклонён за 2 мин 21 с; модель
объявила отсутствующий новый тест существующим, затем присылала лишние правки.
Последняя доработка: runtime вычисляет isNew по файловой системе; при адресном
ремонте лишние изменения карточек и метаданных игнорируются, исходные значения
сохраняются. Схема ремонта ограничивает ID адресными карточками. Проверки области,
связности, доказательств и независимое ревью остаются обязательными.

Проба `guided-sample-20261004094629634`: Plan отклонён — несколько карточек одного
файла и неоднозначная замена новой карточкой. Доработка после пробы: адресное
замечание расширяется на все карточки того же файла, включая сохраняемую карточку;
путь id=0 разрешается после явно заданных удалений. Неоднозначность без явного
выбора сохраняет отказ. Эта последняя доработка проверена регрессионным тестом;
нового живого измерения после неё нет. Полный успех и цель 1–2 модели не подтверждены.

## Сквозная обкатка Gemma, 2026-10-04

Цель: завершение до Handoff с финальным вердиктом, всеми скрытыми тестами,
проверкой честности и не более 30 активных минут. Успешный Plan отдельно успехом
не считается. Одиночные измерения выполняются с сохранением рабочей копии;
код рантайма между началом и концом одного измерения не меняется.

|---|---|---|

| `guided-sample-20261004193454565` | остановка Plan | покрытие claims проверялось раньше добавления runtime-карточек |

Изменения по наблюдениям:

- Генератор тестовой карточки ссылается на полные процедуры приёмки; сохраняет
  содержательные действия, проверки и контракт автора.
- Полнота покрытия проверяется после включения runtime-карточек, до записи плана;
  ошибка перечисляет конкретные непокрытые claims.
- Замечания завершённого независимого ревью возвращаются автору вместе с текущим
  кандидатом. До двух ремонтов, каждый с новым независимым ревью; отрицательное
  решение не подменяется одобрением.
- Схема ремонта разрешает существующие ID. Рантайм восстанавливает ошибочный ID
  по однозначному файлу и сохраняет неадресованные карточки. Отбрасывается только
  полностью пустая новая карточка с буквальным N/A во всех содержательных полях.
- После ремонта номера и ссылки зависимостей перенумеровываются вместе.
  Ссылки на удалённые карточки и повторные ID отклоняются.
- Имя нового теста выбирается из добавляемой функции в «Что делаем», исходного
  запроса или приёмки. Формы «функцией», «функции», «функцию», «функция» распознаются;
  раздел исключений не используется для выбора имени.
- Chunk получает дословный исходный запрос вместе с каноническими требованиями.

Измерение `guided-sample-20261004200416355`, Gemma / add-validator, остановилось
на Plan: относительный спецификатор `from './validate.ts'` в обосновании был принят
за путь от корня проекта. Исправление разрешает такой спецификатор относительно
явно названных существующих исходников только при одном известном адресе; неизвестный
или неоднозначный путь по-прежнему отклоняется, существующий файл требует актуального
доказательства чтения. Односимвольный буквальный реэкспорт в поле symbol переводится
в имя символа; право добавить его проверяется отдельно по задаче и Intent.

После этих исправлений: 87 профильных тестов проходят. Следующее сквозное измерение:
`guided-sample-20261004201025570`, Ministral / add-validator: остановка Ask,
34 запроса разрешения вопросов, 567448 активных миллисекунд. Точные цитаты источников
не подтверждены; ошибочные предположения о Customer не приняты как факты.

Обнаружен и исправлен барьер учёта тестов: результат выполненного runtime-гейта
теперь попадает в ленту как gate_result. Проверка честности принимает его только

### Реализация плана восстановления guided, 2026-10-05

Chunk различает пустой SEARCH, отсутствующий SEARCH, несколько совпадений,
устаревший хэш и синтаксически неверный черновик. Следующий запрос получает
rejectedProposal.diagnostic: вид ошибки, путь, хэш прочитанного файла и
последовательного черновика, индекс edit, число совпадений, фрагменты со строками
и признак необходимости чтения. Фрагменты ограничены 6000 символами суммарно;
для неоднозначного SEARCH показываются первые три места. Отсутствующий SEARCH
заземляется возле символа карточки, если он найден. Диагностика сохраняется в
наблюдении conflict без изменения публичного формата результата. Совпадения
проверяются после предыдущих edits этого предложения; нечётких замен нет.

Plan имеет отдельный режим target: неверную цель можно перенести в исследованный
разрешённый исходник или обязательный новый файл задачи. Модель получает список
допустимых путей и реальные объявления. ID перенесённой карточки сохраняется;
зависимые карточки включаются в адресный ремонт для исправления ссылок при удалении.
Сервер дополнительно проверяет разрешённость переноса, не полагаясь на JSON-схему.
Обычный ремонт не меняет путь. После ремонта остаются обязательными проверки
уникальности карточек, символов, claims, границ и независимое ревью до одобрения.

До завершения guided Intent отдельный контекст той же модели проверяет весь
контракт: область, запреты, инварианты, предположения, приёмку и основания.
Замечания принимаются только с точными цитатами существующих секций и исходного
запроса. Ремонт ограничен адресованными секциями, проходит обычный гейт Write и
перепроверяется независимо. Максимум два ремонта в существующем бюджете запросов;
неполный ответ, чужая цитата, отказ записи, конфликт с внешним изменением или
неустранённое противоречие блокируют этап. Проверка не требует будущей реализации.
Старое состояние читается без миграции; дополнительных прав записи нет.

### Holdout-набор и критерий воспроизводимости, 2026-10-06

Анализ серий 2026-10-05 показал: все задачи, на которых отлаживался guided-флоу
(zero-change-verify, add-validator, cli-flag, rename-field), использовались в отладке
и не являются независимым замером; одиночные успехи на повторах не воспроизводятся
(0/6 закрытий в серии guided-sample-20261005140516192). Утверждены два изменения
практики: отдельный holdout-набор задач и критерий успеха ячейки model×task —
pass в ≥2 из 3 повторов по guidedAcceptance вместо одиночного pass.

Holdout-набор — новое семейство `fleet` (нормы расхода топлива автопарка; домен не
пересекается с отладочными задачами), две задачи со slug-префиксом `holdout-`:
`holdout-winter-surcharge` (regression + precision: зимняя надбавка 15% к сырому
расходу, половина вверх, вся политика в тексте задачи — контроль ложных вопросов)
и `holdout-trailer-rule` (regression + human: надбавка за прицеп +2 л/100 км к норме
класса приходит только из ответа автоответчика — проверка ask-этапа). Обе задачи
отмечены `holdout: true` в expected JSON. Инварианты прогнаны: на нетронутой фикстуре
regression зелёные, precision/human красные (2/6 и 2/5); на эталонном решении все
кейсы зелёные, ни одного пропущенного (6/6 и 5/5). Спека: `bench/specs/fleet.md`.

Агрегация серии повторов добавлена в `bench/run-guided-sample.mjs`: манифест несёт
`cells[]` (model × task → passes/repeats, порог, reproducible), порог выводится из
`--repeats` (≥2/3, минимум два; repeats=1 остаётся скринингом), сводка печатается
по серии. `guidedAcceptance.ts` не менялся: single-run правило строгое, агрегация —
поверх него. Пометка limitations манифеста различает holdout-задачи и известные.

### Норма verify: саморевью — advisory, отдельный review-маршрут, 2026-10-06

Реализована в коде норма verify редизайна «модель решает — рантайм пишет»
(`server/methodology/guided.md`). Вердикт считает рантайм из гейтов этапа, скрытых
тестов (в бенче), проверок честности и сверки diff с деревом — как раньше, но находки
модельного ревью той же моделью, что исполнитель (маршрут chunk), больше не роняют
вердикт: они принимаются в отчёт помеченными `advisory` и рендерятся отдельным
справочным разделом «Справочные находки саморевью», который разбор вердикта не читает.
Решение о маршруте скана — `run/reviewRoute.ts::decideReviewScan`: заданный в конфиге
раннера `reviewModel` (id из config/models.json; env `SDLC_REVIEW_MODEL`), отличный от
исполнителя по provider:model, — блокирующий независимый рецензент, как прежде; не
задан или совпадает — скан идёт маршрутом этапа verify, но справочный. Тот же маршрут
обслуживает независимое ревью проработки на этапе 4 (внутренний фильтр качества плана,
на вердикт не влияет). Это единственное исключение из инварианта «одна локальная
модель в guided»: review-маршрут резолвится вне профиля, и проверка provider:model +
localhost маршрутов профиля его не видит. Ранее в этом документе сказано «все маршруты
профиля, включая ревью» — уточнение относится к маршрутам профиля; `reviewModel`
живёт вне профиля. Пороги guidedAcceptance не менялись.

### Протокол «модель решает — рантайм пишет» в коде, 2026-10-06

Реализовано ядро редизайна по итогам серий 2026-10-05 (26+ прогонов, 0/6
воспроизводимость; доминирующие отказы — byte-exact SEARCH/REPLACE и расхождение
карты плана с кодовой базой). Методология обновлена в `server/methodology/guided.md`
и `preparation-v2.md`; код приведён к ней:

- Chunk: SEARCH/REPLACE заменён операциями над символами (`exec/symbolOps.ts`):
  `replace_body`/`insert_after`/`insert_before`/`rename`/`delete`/`create_file`/
  `ensure_import`. Модель называет символ из показанной карточки (закрытый enum в
  схеме ответа) и генерирует только новое содержимое; позиции, слияние import и
  переписывание ссылок при rename материализует рантайм. Неоднозначный символ —
  отказ с qualified-кандидатами, без угадывания. Сохранены инварианты: транзакционные
  группы, симуляция до первой записи, WAL только собственных байт, запрет полной
  перезаписи существующего файла, TS-валидация, гейты после группы.
- Plan: `steps[].symbol` — enum известных символов из explore-карточек или
  `{"isNew":true,"name"}` (без проверки вхождения в код); склейки имён исключены
  схемой. Ремонтов плана до 3 адресных вместо 8. Пустой enum в json_schema больше
  не генерируется (падение Ollama HTTP 400 устранено, fallback — строка с паттерном).
- Intent/ask: дословные цитаты заменены ссылками `{file, lines:[from,to]}` на
  показанные источники; рантайм проверяет диапазон и сам рендерит цитату в артефакты.
  Ответы человека по-прежнему хранятся дословно.
- Ремонт только с новым входом: одна повторная выборка по той же схеме, дальше —
  адресный ремонт с диагностикой и суженной схемой, иначе split/escalate.
- Удалены домен-специфичные эвристики общего рантайма
  (`guidedPhoneAlternativeTestProblem`, `guidedPlanPhoneAlternativeProblem`).
- Метрика `chunkEvidence.scopeViolation` больше не краснеет при `treeChanged:false`:
  «пути плана без правок» вынесены в отдельный флаг `planPathsUntouched`.

Инфраструктурные исправления той же волны: молчаливое понижение reasoning effort
medium/high→low при обрезанном ответе убрано из FormFill/Guided/GuidedPlan
исполнителей — повтор идёт с тем же effort и удвоенным max_tokens (до 16384), при
невозможности — friction `truncated` и предупреждение в ленту; параметр эксперимента
больше не меняется посреди измерения. На этап explore добавлен per-request таймаут
`limits.exploreRequestTimeoutMs` (дефолт 120 с; аномалия 05.10 — два запроса по
~300 с), оборванный запрос пишет длительность в метрики и предупреждение с именем
файла. Проверки: typecheck чисто, тесты server 2613 / web 144 / bench 349 — все
зелёные. Остаточное: `metricsReport.ts` не показывает `planPathsUntouched` отдельной
колонкой; live-прогон с реальной моделью — отдельный замер.
