# Эксперимент с выбором плана

Режим выключен по умолчанию. На этапе Plan guided можно получить два или три
самостоятельных кандидата, проверить каждый обычным валидатором и выбрать один
типизированным решением модели. Исполнитель, гейты и финальная приёмка остаются
источниками проверки выполненной работы.

## Настройка

В профиле проекта:

```json
"planSelection": {
  "candidates": 3,
  "judgeModel": "<id из реестра моделей>"
}
```

Без `judgeModel` используется модель Plan. `candidates: 1` включает контрольный
режим без оценщика; это позволяет явно назначить другой локальный маршрут только
на Plan через обычный `stages.plan`. Остальные этапы и маршруты ревью guided
сохраняют закреплённую модель задачи. Эксперимент допускает только локальные
OpenAI-compatible маршруты; генератор и оценщик должны использовать одну валюту
бюджета. Jev API и Nimble `/v1/systemone` этим изменением не подключаются.

В CLI стенда:

```powershell
node bench/src/cli.ts --all --task <task-id> --model <generator-id> --execution-mode guided --guided-engine-version 4 --plan-candidates 3 --plan-judge <judge-id>
```

Для одного варианта на другом маршруте: `--plan-candidates 1 --control-plan <id>`.
Параметры выбора передаются отдельно от параметров HTTP-провайдера.

## Поведение

- Кандидаты получают свежий контекст и те же требования, разведку и уточнения.
  Они не видят другие кандидаты и суждения оценщика. Адресный ремонт получает
  замечания валидатора к своему кандидату.
- Проверяются схема, поля, реальные цели и символы, вызывающие, последствия,
  покрытие требований, обязательные карточки, границы Intent и свежесть источников.
  До выбора канонический план не записывается и не архивируется.
- Невалидные варианты исключаются. Полностью одинаковые нормализованные планы
  объединяются; число разных подходов не гарантируется.
- Оценщик видит нормализованные планы, исходные требования и показанные исходники.
  Возможны `select`, `reject_all`, `insufficient_evidence`. Неизвестный ID,
  противоречивый ответ и незавершённый JSON останавливают этап.
- Оценка повторяется с обратным порядком кандидатов. Выбор принимается только
  при совпадении. Это проверка устойчивости к порядку, не доказательство качества.
- Выбранный план повторно проходит обычные проверки и стандартное одобрение записи.
  Изменение входов во время выбора останавливает этап. Отказ не вызывает скрытый
  переход к первому кандидату или прежнему режиму.
- На каждого кандидата отводится до четырёх запросов; общий лимит этапа делится
  между кандидатами с резервом двух оценок и одного прохода финальной проверки.
  Для трёх кандидатов требуется минимум шесть доступных ходов. Все запросы
  расходуют общий бюджет и используют общий сигнал отмены.

Журнал каждого запуска хранится в `.sdlc/<slug>/.runner/plan-selection/<id>.json`:
входной хэш, модели, кандидаты, отказы, ответы в обоих порядках, выбор и расход.
HTTP-обмены оценщика имеют отдельную метку `planJudge` в существующей трассе.
Арбитражные запросы относятся к категории нагрузки `review`.

## Парное сравнение

```powershell
node tools/compare-plan-selection.mjs
node tools/compare-plan-selection.mjs --run
```

Без `--run` выводится матрица без вызовов моделей. Можно задать `--generator`,
`--judge`, `--tasks`, `--repeats`, `--stage-minutes`, `--run-minutes`, `--max-turns`.
Сила отдельного оценщика является гипотезой, а не выводом из ранга реестра.
Для повтора на готовом входе одной задачи доступен `--input-snapshot <имя>`
вместе с `--tasks <task-id>`. Снимок должен относиться к этой задаче, быть снятым
после Ask и содержать guided той же версии движка. Старые произвольные снимки
не переводятся в guided. Продолжение со снимка проверяется по сохранённому режиму
и версии движка. `--control-plan` разрешён только при явном `--plan-candidates`;
другие control overrides в guided сохраняют прежний запрет.

Для каждой задачи сохраняется один вход после Ask; четыре режима продолжают
одну и ту же копию входа: один план, три кандидата с собственной моделью,
три кандидата с отдельной моделью и один план на отдельном маршруте.
В остальных этапах используется один и тот же генератор. Лимиты времени,
стоимости, ходов и попыток одинаковы; фактический расход может отличаться.

Серия выполняется последовательно, чтобы не конкурировать за локальную GPU.
При изменении производственного кода серия прекращается. Manifest, журналы и
сводка находятся в `bench/results/plan-selection-<timestamp>/suite.json`.
Успех требует завершения всего витка, положительной финальной приёмки,
прохождения всех скрытых проверок и отсутствия подтверждённых нарушений честности.
Прохождение Plan отдельно не считается успешной задачей.

Один повтор — пилот работоспособности. Он не устанавливает статистически надёжную
прибавку качества. Для вывода нужны повторные серии и удержанные задачи с другими
путями, символами и формулировками. Наличие правильного варианта среди всех
кандидатов отдельно не измеряется: остальные планы не реализуются. Проверки
символов и вызывающих сохраняют текущие языковые ограничения Runner.

Отдельная проверка компонента на фиксированных входах:

```powershell
node tools/plan-selection-pilot.ts
node tools/plan-selection-pilot.ts --run --generator <id> --judge <id> --minutes 3
```

Её задачи и исходники находятся в `bench/experiments/plan-selection-cases.json`.
Она проверяет работу Plan и выбора на подготовленных требованиях без заполнения
Intent моделью. Входы воспроизводимы, но этот пилот не проверяет выполнение Chunk,
скрытые тесты результата или качество всей методологии. Матрицы компонента и
полного витка оцениваются отдельно.
