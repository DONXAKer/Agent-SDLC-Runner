
# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Рабочий язык репозитория — русский: комментарии, сообщения об ошибках, тексты в UI и
коммиты. Пиши так же.

## Команды

```bash
npm install
npm run dev            # сервер :8030 + UI :5130 — только под bash (в строке скрипта `&`)
npm run dev:server     # под PowerShell запускай два окна: dev:server и dev:web
npm run dev:web
npm run build          # typecheck server + vite build web (статику раздаёт сервер)
npm test               # node --test: server + web + bench
npm run typecheck      # tsc --noEmit по server и web

docker compose up -d   # прод: см. Dockerfile, .env.example
```

Прод исполняет **TypeScript напрямую**, как и dev: пакет `shared` экспортирует сырой `.ts`,
то есть Node всё равно снимает типы на лету, и собранный `dist` был бы вторым рантаймом с
собственным поведением. Поэтому `server build` — это `tsc --noEmit`, а собирается только
`web`: его статику раздаёт сам сервер. Адрес прослушивания задаётся `SDLC_HOST`
(по умолчанию петля; в контейнере `0.0.0.0`, границей служит публикация порта).

Один файл тестов и один кейс (из каталога `server/`):

```bash
node --import ./test/setup-state.ts --test test/policy.test.ts
node --import ./test/setup-state.ts --test --test-name-pattern "лексер" test/policy.test.ts
```

`--import ./test/setup-state.ts` даёт процессу временный `SDLC_STATE_DIR`: без него тест,
доходящий до вердикта этапа 6, пишет в настоящий `~/.sdlc-runner` машины.

Тесты — штатный `node:test` (`describe`/`it`, `node:assert/strict`), без фреймворка.
Ни линтера, ни форматтера в проекте нет: `typecheck` и есть проверка.

## Как это устроено

Тонкий сервис под **один виток методологии Agent-SDLC**: семь этапов
`intent → explore → ask → plan → chunk → verify → handoff`, с видимым промптом, одобрением
каждой записи до её применения и учётом стоимости. Целевой проект — чужой каталог
(`projectRoot` из конфига), а не этот репозиторий.

Три workspace'а: `shared` (типы контракта), `server` (Fastify + WebSocket), `web`
(React 18 + Vite + Tailwind 4, dev-порт 5130 с прокси на 8030). В проде сервер раздаёт
`web/dist` статикой.

### Состояние витка живёт на диске, а не в памяти

Артефакты пишутся в `.sdlc/<slug>/` **целевого проекта** в каноническом формате методологии
— их читают и существующие скиллы `/sdlc-*` Claude Code. Поэтому предусловия этапа
(`server/src/run/stages/**`) проверяются чтением файлов, а не памятью диалога: виток
переживает перезапуск сервиса, начатый в терминале продолжается здесь и наоборот.
`server/src/artifacts/paths.ts` — единственное место, где имена артефактов превращаются в
пути; короткие ключи (`plan`, `journal`, …) существуют, чтобы клиент не мог назвать
произвольный файл на диске. Полнота `intent.md` считается ОДНОЙ функцией на страж
завершения этапа 1 и предусловия этапов 2/4 (`stages/preconditions.ts::intentFilled`):
секция «Что придётся тронуть» законно пуста до разведки, а на мелком контуре — всегда;
две разные проверки одного файла давали `ok⚠` на этапе 1 и «не стартовал» на этапе 4
(test28, 2026-09-23).

Рядом с артефактами методологии там же лежат СЛУЖЕБНЫЕ файлы рантайма — они не артефакты,
под `ArtifactKey` не подпадают и скиллами не читаются: `.events.ndjson` (лента событий),
`.chunk-N-baseline.json` (снимок грязного дерева) и числа витка — `metrics.json` (полный
снапшот `RunMetrics`) с рендером `metrics.md` (`run/metricsReport.ts`). Снапшот пишется в
`finally` каждого этапа, а не только на handoff: виток, умерший до этапа 7, прежде оставлял
одну сырую ленту. Он же и восстанавливает накопители при пересоздании `Run` — метрики
переживают рестарт тем же приёмом, что chunk/attempt из журналов. Второго источника чисел
нет: `metrics.md` рендерится из того же снапшота, история попыток остаётся в `iterations.md`,
лента — в `.events.ndjson`.

**Вердикт попытки** живёт НЕ в каталоге витка, а в состоянии рантайма этой машины:
`<SDLC_STATE_DIR или ~/.sdlc-runner>/verdicts/<проект>/<слаг>/chunk-N-attempt-K.json`
(`run/verdictStore.ts`). Это единственный источник «попытка принята» для handoff (коммит!),
предусловия chunk, `/advance` и восстановления после рестарта. Секция «Вердикт» отчёта
приёмки — копия для человека: отчёт пишет и модель этапа 6, и её `passed: true`, записанный
до отмены этапа, открывал handoff с коммитом. Вне проекта файл недосягаем для инструментов
модели по построению; до этого он лежал в каталоге витка, и `cp`/`mv` в Bash (лексер их
сознательно не видит) подделывали его, а подпись HMAC, закрывавшая это, принесла ключ,
терявшийся с контейнером, и запреты по имени, бившие по проектам. Цена раскладки: вердикт
привязан к машине и пути проекта — в docker состояние на томе (`SDLC_STATE_DIR=/state`),
тесты получают временный каталог (`server/test/setup-state.ts` через `node --import`).

Нет вердикта — нет «принята»: чтения «по старинке из отчёта» нет намеренно; витку, начатому
до этой раскладки, улики проверенной попытки бережёт журнал итераций (`attemptJudgedInLog`).
Вердикт хранит хеш патча попытки: патч, переписанный после вердикта, закрывает handoff
предусловием и `/advance chunk` (`stalePatchReason`), а дерево, ушедшее от патча, — коммит
(`handoff.ts::staleVerdictReason`, исход коммита пишется в отчёт передачи). После коммита в
вердикт пишется его sha (`markCommitted`), и повторный вход в handoff сверку дерева не
делает: дерево чистое, патч уже в HEAD. Вход в verify прежний вердикт НЕ снимает —
отменённый повтор оставлял попытку без вердикта, и chunk перезаписывал её улики. В коммит
служебные дот-файлы витка не идут (`isRuntimeServiceName`). Восстановление после рестарта
оставляет виток на последней начатой попытке при любом вердикте — следующую открывает
только «Новая попытка» (`advanceProblem` проверяет бюджет и `escalate`), а улики
проверенной попытки бережёт предусловие chunk.

### Дашборд запусков читает диск и `Run` не поднимает

`server/src/dashboard/` собирает карточки всех витков всех проектов конфига и прогонов
стенда (`GET /api/dashboard`, детали и файл — `/api/dashboard/:source/:project/:slug[/artifact?name=]`,
экран `#/dashboard`). Архивному витку `Run` не создаётся никогда: конструктор пишет
`.runner/.gitignore` в каталог витка. Поэтому всё, что живая ручка считала через `run.ctx`,
вынесено в чистые функции от `StageContext`, и их зовут ОБЕ поверхности:
`run/stageInfo.ts` (пройден / решение записано), `run/stages/entry.ts::entryProblems`
(тело `Run.blockerDetails`), `run/metricsSnapshot.ts` (один читатель `metrics.json`,
им же восстанавливается `Run`). Второй копии расчёта в `index.ts` быть не должно, это
держат `stageInfo.test.ts` и `entryProblems.test.ts`.

Источник витка косвенный: этапы запускал раннер (в ленте есть прогоны этапов) или есть
числа витка (`metrics.json`) — это `ui`, иначе `terminal`. Каталог `.runner/` признаком НЕ
служит: его создаёт конструктор `Run` при простом открытии витка, и терминальный виток,
однажды открытый в интерфейсе, навсегда становился `ui` (`dashboard/witoks.ts::witokSource`). Имена
конфига с одним корнем сводятся в один проект (`canonicalRoot`, тот же ключ, что у
вердиктов). Стенд читается своим узким разбором (`dashboard/bench.ts`), а не импортом
`bench/src`: стенд сам импортирует сервер, и `bench/` может не быть в образе. Файлы
отдаются только по имени из словаря (`dashboard/artifactAccess.ts`) со сверкой `realpath`.
Вердикт на деталях берётся только из `verdictStore` этой машины, а не из строки `passed:`.
Опрос раз в 5 с держится кэшами: подпись каталога витка, mtime файла стенда, LRU ленты и
ETag списка (сотни прогонов стенда весят мегабайты).

Идущий прогон стенда виден до своего `result.json` по машинному файлу
`bench/traces/<slug>/run-state.json` (контракт `BenchRunState` в `shared`, пишет
`bench/src/runState.ts`): pid процесса, рабочая копия, отметки этапов, остановка и «результат
записан», плюс машина, пульс (`heartbeatAt`, раз в `BENCH_HEARTBEAT_MS`), этап старта
драйвера и валюты маршрутов. Жив ли прогон — свежий пульс И (на той же машине) живой pid:
pid на Windows быстро переиспользуется, а в контейнере он чужой. Разбор человекочитаемого
`progress.log` оставлен только запасным путём для прогонов до этого файла
(`dashboard/benchProgress.ts`). Лента в подпись кэша витка не входит — её сводка
дочитывается по смещению (`dashboard/events.ts::readEventSummary`); прогон в ленте
принадлежит своему `runId`, и новый `run_started` закрывает незакрытые этапы умершего
процесса. Порядок карточек и правило «где виток» (`web/src/lib/dashboardStages.ts::focusStage`)
решает только клиент.

Старые прогоны стенда лежат в `bench/archive/{results,traces}` той же раскладки
(`bench/src/archive.ts`, `npm run bench:archive`: на месте один прогон на базовую модель — последний)
и читаются вторым `BenchIndex` с проектом
`archive` (`DASHBOARD_BENCH_ARCHIVE`): проект у карточки стенда выбирает КАТАЛОГ, а не
подписывает её. На доске архив скрыт, пока его не выбрали фильтром проекта: сотни старых
карточек заслоняли текущую картину.

### Этап витка — модуль `server/src/run/stages/`

У каждого этапа свой файл (`intent.ts`, `explore.ts`, `ask.ts`, `plan.ts`, `handoff.ts`) или
каталог (`chunk/`, `verify/`): определение (`StageDef` — права, артефакты, предусловия) и всё,
чем этап отличается в рантайме. `Run.runStage` — общий каркас без ветвлений по имени этапа: в
точках, где этапы ведут себя по-разному, он зовёт хуки `StageModule.begin(host, route)` →
`StageInvocation` (факты промпта, автозаполнение, страж завершения, доборы после хода,
дозаполнение, улики, вердикт) в фиксированном порядке — порядок фаз и есть поведение. Модули
видят виток только через фасад `StageHost` и не импортируют `Run.ts` как значение.

Держат это два теста: `stageModules.test.ts` (реестр, запрет импортов, нет `stage === '…'` в
`runStage`/`finishFormArtifact`) и `runStageGolden.test.ts` — сквозной виток на подменной модели
с эталоном событий, запросов и файлов (`UPDATE_GOLDEN=1` — только на коде, в поведении которого
уверены). Фасад `run/stages.ts` оставлен для прежних импортов: новых символов туда не добавлять.

### Два флоу — одна форма вызова и одно решение политики

Это главный инвариант кодовой базы, и почти вся его защита — в структуре, а не в тестах.

- `SdkExecutor` (флоу `sdk`, `@anthropic-ai/claude-agent-sdk`, Max-подписка) и
  `LoopExecutor` (флоу `loop`, свой цикл tool-use для Ollama/vLLM/LM Studio/OpenRouter)
  реализуют один `StageExecutor` и различаются ровно двумя вещами: кто крутит цикл и кто
  исполняет инструменты.
- `server/src/exec/normalize.ts` — **единственное** место, где различия имён и аргументов
  инструментов вообще имеют значение. Дальше по течению все видят `NormalizedCall`.
- `server/src/policy/index.ts` — **единственная** точка решения. Реэкспортов из неё нет
  намеренно. Проверки ленивые и порядок значим: `stageTools → denyList → pathScope →
  planScope`, чтобы отказ называл самую раннюю причину.
- `server/test/conformance.test.ts` гоняет одну таблицу вызовов в обеих формах и требует
  совпадения и `NormalizedCall`, и вердикта политики.

Правя любой из двух исполнителей, проверь, не появилось ли в нём второе место, принимающее
решение о доступе. Инструменты флоу `loop` (`server/src/exec/tools/index.ts`) политики не
содержат по построению — каждый вызов уже прошёл гейт.

Незнакомый инструмент нормализуется в `unknown`, а не отбрасывается: политика обязана
считать его записью по худшему случаю.

### Внешние MCP-серверы

Раннер умеет давать агенту инструменты внешних MCP-серверов — тех же, что описаны в
`.mcp.json` целевого проекта. Устройство держится на четырёх решениях:

- **Имя одно на оба флоу** — `mcp__<сервер>__<инструмент>`. Разбирает его `parseMcpName`
  (`exec/normalize.ts`); имя `sdlc` зарезервировано за нашим in-process сервером, иначе
  неизвестный `mcp__sdlc__*` превратился бы из `unknown` в вызов несуществующего сервера.
- **Класс инструмента задаёт человек**, а не эвристика и не аннотация сервера:
  `readOnlyHint` — утверждение той стороны, которую гейт сторожит, а имя не гарантирует
  ничего (`tick_world`, `pie_start`, `compile_blueprint` читающими не являются). Отсюда два
  права вместо одного — `McpRead` и `McpWrite`: без этого read-only субагент (`sdlc-locator`)
  получал бы `delete_asset` вместе с `asset_exists`.
- **Аргумент считается путём файловой системы только по объявлению** (`pathArgs`).
  `/Game/Cards/BP_Card` проходит `isAbsolute` и лежит «вне проекта»: скан «строк, похожих
  на путь» отклонял бы каждый вызов с ассетом Unreal отказом, который оператор снять не
  может. Объявленные пути проверяются подстановкой `read`/`write` в те же `denyList`,
  `pathScope` и `planScope` — своих веток у MCP там нет.
- **Набор ограничен потолком** (`mcp.maxInlineTools`, умолчание 12). Один generic-сервер
  Unreal отдаёт 175 инструментов: их описания со схемами — порядка сорока тысяч токенов,
  вдвое-втрое больше всего контекста локальной модели. Отбор считает `mcp/select.ts` —
  чистая функция, и её результат приходит в оба флоу через `ExecRequest.mcp`, потому что
  список для показа оператору и список для модели обязаны быть одним и тем же.

Права `McpRead`/`McpWrite` выдаёт РАНТАЙМ по конфигу этапа (`Run.toolsFor`), а не определение
этапа: `stages/**` общие для всех проектов и про MCP знать не может. Живой прогон поймал это
дорого — инструменты модели выдавались, вызов доходил до политики и отклонялся ею, потому что
права не выдавал никто. Класс правила считается одной функцией (`effectiveMode`) и для прав,
и для политики: посчитай их по-разному — и формально выданное право не сработает.

Соединения: во флоу `sdk` их держит Agent SDK (конфиги уходят в `mcpServers`), во флоу
`loop` — свой `McpHub` поверх `@modelcontextprotocol/sdk`. Поднимаются лениво на этап,
гаснут на конце ВИТКА: погасив редактор между chunk и verify, мы отняли бы у верификации то
состояние, которое она проверяет. Недоступный сервер — обычное дело (редактор выключен), и
он не роняет ни загрузку конфига, ни этап: причина уходит в панель MCP и отдельной строкой
в промпт («выполнить нельзя — напиши это, не изображай выполнение»). Ошибкой загрузки
считается только описание, которое верным само не станет: неизвестный транспорт, `http` без
`url`, ссылка на необъявленный сервер.

Картинки в контекст не попадают никогда: скриншот PIE в base64 — это десятки тысяч токенов.
`mcp/content.ts` кладёт их в `.sdlc/<slug>/mcp/` и отдаёт модели путь.

### Прогоны моделей записываются в журнал

`docs/model-runs.md` — сравнение моделей и ничего кроме: что крутили, помогло ли, во что
упёрлись. Устройство раннера, находки по целевому проекту и прочий контекст туда не пишутся —
файл читают, чтобы выбрать модель и настройку, а не чтобы изучать сервис. Обязательные части
записи: **во что упёрлись** («не справилась» наблюдением не является, «окно 4096, сумма
вход+выход упёрлась в него ровно» — является) и **помогла ли настройка**, включая честное
«не измерено».

Файл дописывается, а не переписывается: опровергнутый результат помечается отозванным рядом с
новым. Два правила опыта, выученных дорого: менять между прогонами только одно — модель либо
одну настройку, и иметь контрольный прогон на конфигурации с подтверждённой диагностикой.
Ранг или размер модели не доказывает её пригодность; обязательной «более сильной» модели нет.

**`docs/model-task-matrix.md` — сводная таблица «модель × задача bench», не журнал.** В
отличие от `model-runs.md` (дописывается, история важна), матрица — результирующее
состояние: раздел на задачу, в его таблице одна строка на модель, столбцы — этапы витка
и «Итого», в клетке — чем кончился этап у этой модели. Заполняется тем же прогоном, что пишет запись в
`model-runs.md`. Когда находка из клетки ПОЧИНЕНА (код исправлен, живой прогон это
подтвердил) — клетка ПЕРЕЗАПИСЫВАЕТСЯ новым исходом, а не копит рядом устаревший текст
о старой проблеме: подробности самого дефекта и фикса остаются в `model-runs.md`
(append-only), матрица показывает только текущее положение дел.

**Фикс в раннере, снятый по находке bench-серии, замеряется той же серией повторно.**
Правка кода/конфига, мотивированная узким местом моделей (не рефакторинг, не багфикс
стенда) — не готова коммитом одних тестов: следующий шаг тот же, что открывал находку,
— серия bench по тем же моделям и задачам (порядок — «Быстрый старт» выше), и по её
итогу дописывается запись в `docs/model-runs.md` (что чинили, помогло ли, во что упёрлись
теперь) и перезаписываются клетки `docs/model-task-matrix.md`/строки
`docs/model-strengths-weaknesses.md` для тех моделей, чья картина сдвинулась. Без этого
шага фикс остаётся недоказанным: тесты ловят регресс в коде раннера, а не отвечают на
вопрос «модель теперь проходит дальше».

**`docs/model-error-taxonomy.md` — таксономия классов ошибок моделей, тоже результирующее
состояние, не журнал.** Строка на КЛАСС ошибки (не на модель и не на задачу — это покрыто
`model-task-matrix.md`), два вида — исполнитель (спотыкается на своём этапе) и рецензент
(пропускает дефект на verify), с разным знаменателем частоты (обычные прогоны против
посевов). Построена по диагнозам, уже написанным в `model-runs.md`, без переразбора сырых
трасс. Раздел «Помогает ли смена модели» в конце — прямой ответ, для каких классов
разведение моделей по этапам работает, а для каких нужен код/гейт/промпт-фикс. Дополняется
тем же коммитом, что вносит в `model-runs.md` находку нового класса, или когда открытый
класс закрывается.

**Каждый новый замер обновляет и методологию.** В репозитории методологии (путь — машинный,
не хардкод: `methodologyDir` из `runner.json`/`runner.local.json` либо переменная
`SDLC_METHODOLOGY_DIR`, см. «Конфигурация» ниже) живёт каталог `model-runs/` —
результирующие карточки моделей (задача · по этапам · сравнение с эталоном · метрики ·
вердикт) и сводный README с таблицами этапов 1–4, этапа 5 и рецензентов. После каждого
прогона bench с новым результатом (новая модель, изменившийся вердикт, новая ручка) туда
вносится обновление тем же коммитом дня, что и запись в `docs/model-runs.md`: карточка
модели и — если сдвинулась общая картина — сводные таблицы. История отдельных прогонов
туда не пишется (она в `bench/results/` и журнале) — только результирующее состояние.

### Политика: четыре уровня, чистые функции

`denyList` (нижняя граница, конфигом не ослабляется), `pathScope` (границы проекта; каталоги
методологии открыты **только на чтение**), `planScope` (запись только в `files_to_touch`
одобренного плана; исключение для `.sdlc` сужено до своего витка и не покрывает решения
человека), `stageTools` (права выдаются на шаг). Все — без I/O, обе стороны зовут их
одинаково.

`shellRedirects.ts` — настоящий маленький лексер целей записи в bash-командах (`>`, `>>`,
`>|`, `tee`, рекурсия в `sh -c`), порт из Java-платформы AI-Workflow; регулярка здесь уже
ломалась в обе стороны. Не заменяй его регуляркой.

Запись СВОЕГО артефакта этапа не по его пути — голое `clarification-report.md`, опечатка в
слаге — это ошибка адресации, а не границы: `approval/artifactAddress.ts` подставляет
канонический путь из `stageArtifacts` ДО политики (той же картой, что резолвит `FillField` по
ключу), и исполнитель получает исправленный вход через `updatedInput`, как при
`repairErasedDecisions`. Политика судит уже канонический путь, защищённые артефакты
отклоняются как прежде, файл плана с тем же базовым именем не трогается. До этого серии
test27–test29 ставили таким записям метку «опасна», а этап оставался без артефакта.

Вне проекта на чтение открыты каталоги методологии и — только во флоу `sdk`, решением по
вызову (`meta.sdk` исполнителя) — `tool-results/` ТЕКУЩЕЙ сессии Claude Code
(`PolicyContext.harnessResultsRoot` из `transcript_path` хука): туда харнесс кладёт длинный
вывод команд и отдаёт модели путь.
Сессии человека и прошлые прогоны того же проекта закрыты — их вывод может нести то, что
закрывает `readDenied`.

Проверка побега через symlink требует диска и потому живёт не в политике, а в
`approval/gate.ts`. Там же значим порядок: **предпросмотр строится только после того, как
политика разрешила вызов** — иначе отклонённый `Write ~/.ssh/id_rsa` успевал прочитать файл
и разослать содержимое в шину событий.

### Этап 6 устроен как конвейер рантайма, а не как поручение модели

Ровно то, что делает программа, модель не делает: `Run.runVerifyGates` прогоняет гейты,
`diffStillMatchesTree` сверяет патч, `verifyAutofill` заполняет таблицу гейтов и шапку,
`runReviewerDirectly` **сам запускает `sdlc-reviewer`** отдельным прогоном и подаёт его
ответ блоком во вход этапа, `verdict/verdict.ts` считает вердикт. Adapter-блок промпта
вычитает эти фазы из эталонного текста скилла явно — иначе дешёвая модель тратит ходы,
пытаясь исполнить Phase 0/1/4.3, для которых у неё нет `Bash` по построению.

Модели остаются §1–§5, и для них есть структурированный канал: `RecordClaim`/`RecordFinding`
(нормализация — в общем `normalize.ts`, рендер — `run/verifyReport.ts`). Таблицу рисует
рантайм, поэтому `verdict/collect.ts` разбирает её по построению; сам `collect.ts` при этом
не менялся — отчёт остаётся тем же документом, что пишет терминальный `/sdlc-verify`.
Ссылка записи сверяется с патчем попытки (`anchorFound`): запись без привязки не
выбрасывается и не роняет вердикт — уходит отдельной строкой. Тем же правилом зеленеет
гейт «Ревью независимым агентом»: прогон, в ответе которого нет ни одного места из патча,
ревью не является (класс «оформитель», r9).

Две ручки этапа выключены по умолчанию и заведены под замер: `ModelDef.claimFill` —
поклаймовый добор (`run/claimFill.ts`, срез патча под пункт из `claimEvidence.ts`) и он же
у дополнительного маршрута ансамбля — узкие вопросы по неуверенным пунктам вместо полного
второго ревью. Статусы маршрутов по-прежнему сводятся по худшему: сильная модель не
перекрашивает `⚠` слабой в зелёный.

Смежное: `limits.maxIterationsByStage` (у verify 60 — замер r9), `PolicyContext.readDenied`
(отчёты прошлых попыток закрыты на чтение — независимость ревью конструкцией, а не
задним числом; поиск, который мог бы их задеть — Grep без фильтра имён от корня или по
каталогу витка, Glob с шаблоном, накрывающим их имя, — отклоняется. Фильтр понимается в
семантике `rg --glob` одной функцией на политику и на `Grep` флоу `loop`
(`policy/paths.ts::compileSearchFilter`: исключающий `!`, шаблоны через пробел или запятую
вне `{}`, `./`; явное исключение `!.sdlc/**` поиск не закрывает), а `type`
ripgrep'а переводится в тот же шаблон в `normalize.ts`), `ExecRequest.progressSignal`
(анти-цикл считает прогресс по принятым записям, а не по повтору вызова).

Гейт «Ревью независимым агентом» зеленеет по ОДНИМ планкам на обоих путях — прямой прогон
рантаймом и `Task` модели, через один контракт `verify-review-v1`
(`reviewValidate.ts::parseReviewText`, вызывается `acceptReviewText`; во втором случае —
хуком `StageInvocation.reviewAccepted` и по полному, не обрезанному ответу): `claims` — ровно
те id, что в задаче, статус из словаря, у `passed`/`failed` — ссылка на место из патча. После
повторного запроса полноту листа судит повторный ответ целиком (не склейка с первым).

### Гейты и вердикт

Автоматические гейты идут **перед** ревью и прогоняются рантаймом (`Run.runVerifyGates`), а
не по просьбе в промпте. Набор берётся из `.sdlc/gates.md` целевого проекта
(`gates/gatesFile.ts`): где в колонке «Чем реализован» стоит команда в обратных кавычках —
выполняется она, где проза — берётся встроенная реализация по имени из `BUILTIN`
(`gates/builtin/index.ts`). Обязательная пятёрка проверяется на старте **каждого** этапа
кроме `intent`. Кто отчитывается за строку без скрипта, решает ОДНА таблица
(`verify/gates.ts::reportedBy`/`UNSCRIPTED_GATES`): «Сверка отчёта с набором» — рантайм,
гейты проверяющего — рецензент; такие строки рантайм не «прогоняет» (прогон давал им
`⏭ исполнить нечем`, и тот ронял каждую попытку худшим из двух). Команда в обратных
кавычках побеждает имя — строка исполняется, как любая, — кроме ревью: его статус всегда
факт прогона рецензента (`externalGateStatuses`), строку заполняет модель.

Запрет на вызов `cmd`/PowerShell — только для команд МОДЕЛИ (`denyList.ts::DENIED_MODEL_ONLY`).
Совпадение — по слову-команде в любом месте строки: имя, перед которым нет символа пути или
имени, в кавычках тоже; явный путь к `cmd.exe`/`powershell.exe`; `cmd` с флагом, с вводом из
файла или из пайпа. «Позиция вызова» пропускала обёртки (`xargs pwsh`, `env powershell`) и
перевод строки, «слово где угодно» било по `go test ./cmd` и `docs/powershell.md`; осталась
принятая цена — `grep -rn powershell src` отклоняется. `Bash` модели на Windows исполняется
только Git Bash'ем (`gates/shell.ts::posixShell`, `SDLC_BASH_PATH`; в docker-песочнице — `sh`
контейнера); не нашёлся — отказ с причиной, а не молчаливый `cmd.exe`. Команды гейтов из
`.sdlc/gates.md` пишутся под платформу оператора (`powershell -File test.ps1`,
`.\gradlew.bat test`) и исполняются её шеллом: для них действует общий пол без этого
запрета, а запись модели в `gates.md` — как любая запись, через одобрение человека.
`blocked_env` — только гейты класса среды (`verdict.ts::ENV_CLASS_GATE`): «сборка»/«тесты»
отдельным словом, основа «компил…», установка зависимостей (имя с «Зависимост…» или
«установка/восстановление зависимостей»); аудит, уязвимости, лицензии, сверки и
архитектурные проверки зависимостей — не среда.

Вердикт (`verdict/verdict.ts`) — чистая функция по таблице методологии: любое из условий
роняет результат, `⏭` снимается только строкой неприменимости, подписанной **именем**
(планка формы: «колонка "Утвердил" без имени = артефакт не заполнен»), при расхождении
отчёта рецензента с фактическим прогоном в вердикт идёт **худший** из двух статусов.
Единственное исключение — гейты из `runtimeAuthoritativeWhenGreen` (сегодня там только
«Ревью независимым агентом»): состоявшийся вызов субагента рантайм видел своими глазами, и
`⏭` отчёта («не запускался») его не опровергает; `❌` отчёта побеждает по-прежнему. Смысл в
том, что слабая модель может ошибиться в статусе, но не может выдать ложный зелёный. Ничего
из этого не должно начать спрашивать модель.

### Оси прод-готовности разбираются на этапе 4, а не советами на этапе 6

Гейт набора **«Разбор последствий»** (этап 4, выключаемый) требует от плана строку на каждую
из шести осей канона — безопасность, ресурсы и скорость, отказы зависимостей, настройки,
совместимость и данные, наблюдаемость — и на каждую исход из ЗАКРЫТОГО словаря: `claim-N`,
инвариант, включённый гейт, принятый риск, следующий виток, `н/п` с причиной. Свободный текст
исходом не считается по построению: рекомендация, оставшаяся текстом, не имеет исполнителя
(`SDLC.md` → «Когда дефект проскочил»).

**Ключевое место — адресат исхода, а не сам исход.** `artifacts/planAxes.ts` сверяет
`claim-N` с пунктами задачи, имя гейта — со ВКЛЮЧЁННЫМИ строками набора, «следующий виток» —
с открытым вопросом задачи, «инвариант» — с секцией инвариантов, «риск» — со строкой таблицы
принятых рисков. Без этой сверки гейт проходится словарём слов: ревью показало план, где все
шесть осей закрыты строками «claim-99», «гейт „Такого нет“», «следующий виток», и разбор давал
ноль проблем. Факты приходят готовым `AxisContext` из `stages/plan.ts::axisProblems` — сам разбор чистый.

Класс исхода считается по ПЕРВОМУ ключевому слову в ячейке, а не фиксированным порядком
проверок: «гейт „Секреты в diff“ — риск утечки закрыт» это гейт, «риск — см. claim-3» это
риск, «следующий виток: оценить риск» это следующий виток. Порядок проверок читал все три
неверно.

Добор осей, о которых модель ничего не сказала, — топ-ап ПОСЛЕ хода (ручка
`ModelDef.planAxisFill`, симметрично `claimFill`) в двух формах: пошаговый
`run/planAxisStepwise.ts` (`'stepwise'`) и комбинированный `run/planAxisFill.ts`
(`true`/`'combined'` — `true` оставлен за комбинированным, под ним записи замерены, и смена
смысла под тем же id смешала бы механизмы в матрице; иное значение — ошибка профиля). Пошаговый задаёт по одной степени свободы на вопрос —
«затронута?» по всем осям, причины незатронутых, «что именно» затронутых, исход по одной
оси одним ключом из перечисленных КОНКРЕТНЫХ адресатов, поля риска — потому что
комбинированная строка из 3–6 полей на шесть осей одним ответом у слабых моделей не
разбиралась вовсе (test29, 2026-09-23: топ-ап состоялся технически и не дал ни одной
клетки). Вопрос и разбор
опираются на закрытый словарь `run/axisOutcomes.ts`: модель отвечает КЛЮЧОМ из явно
перечисленного списка — тот же приём, что `ChoiceOption`/`matchChoice` для choice-полей
бланка, — а словоформы ключей общие с чтением плана (`OUTCOME_WORD_SOURCES` из
`planAxes.ts`): что топ-ап запишет, читатель обязан прочитать обратно, и два набора
словоформ уже расходились (`RISK_HEAD` повторял группу окончаний `OUTCOME_WORDS`). Исход
без ключа словаря ответом не считается: ось остаётся открытой для стража завершения,
вместо того чтобы в план уходил текст, который `planAxisProblems` сам же отвергнет.

**Подписи под принятым риском нет намеренно.** Риск — часть плана, и человек принимает его
полем «Одобрение»; подписная колонка в таблице была бы вторым каналом решения, которого у
человека в этом файле нет: заполнить её агент не вправе, а `setDecision` работает по метке
поля, а не по ячейке таблицы. От строки риска требуется другое — причина и **когда вернуться**.

Проверка зовётся из **стража завершения этапа 4** (`stages/plan.ts::axisProblems`), а не предусловием
этапа 5: находка нужна модели в её собственном ходу, иначе дописывать исход после ухода
планировщика становится некому (тот же случай, что `explorationPathProblem`, r32). Страж
уважает и `reportsAt`: гейт, перенесённый проектом на другой этап, здесь не проверяется.
Строку набора для обоих потребителей (страж и перенос статуса в отчёт) выбирает одна
функция `stages/plan.ts::axesGateRow`: два места решения о статусе гейта расходились бы при первой же
правке критерия.

В отчёт приёмки недоведённый разбор идёт **`❌`, а не `⏭`**: рантайм знает не «не
запускалось», а «проверено и провалено», а `⏭` снимается подписанной строкой
неприменимости (`verdict.ts`) — то есть измеренный программой провал можно было закрыть
подписью. По той же причине отсутствие `plan.md` или `intent.md` даёт ПРОБЛЕМУ, а не
пустой список: пустой означает «разбор доведён», и молчание зеленило гейт по
несуществующему артефакту.

Страховка на этапе 6 — четвёртый угол рецензента. Он смотрит ВСЕ строки: и «не затронута»
против diff'а, и заявленные исходы против артефактов. Отдельного условия вердикта у неё нет
намеренно: находка идёт подтверждённым расхождением, которое роняет вердикт первым из семи
условий, поэтому `verdict/verdict.ts` и `flow-verdict.py` не менялись. Чувствительность угла
меряют посевы `axis-config-blind` и `axis-secret-in-log` (`bench/src/seeds.ts`) — оба невидимы
автоматике по построению и якорятся ВНЕ `priceFor`: её задача фикстуры обязывает переписать,
и посев туда мерил бы везение, а не находимость.

### Промпт

`prompt/build.ts` читает тело этапа из `SKILL.md` эталона в `runner.skillsDir` **в рантайме**
— копий текстов этапов в репозитории нет, и заводить их не надо. К телу добавляется adapter-
блок, описывающий отличия от интерактивной сессии Claude Code. Всё, что уйдёт в модель,
собрано в одной функции: промпт уходит в шину до вызова исполнителя и редактируется
оператором, поэтому ничего не должно подмешиваться позже и незаметно (см. предупреждение про
отредактированный промпт в `Run.runStage`).

### Схема формы вместо сплошного текста бланка (`compactForms`)

Формат артефактов на диске — контракт: его читают терминальные скиллы `/sdlc-*` и парсер
эталона `flow-verdict.py`, и менять его нельзя. Но между моделью и этим форматом стоит
слой, который снимает измеренный класс сбоя (`docs/model-runs.md`): 44 промаха `Edit` на
пять рабочих копий из-за переноса строки внутри поля шаблона, менюшные поля с обеими
ветками, лист приёмки из одного пункта строки-образца.

`server/src/artifacts/formSchema.ts` выводит из текста бланка **схему** (поле → вид: scalar
/ choice / list / records / decision / mechanical, допустимые значения, минимум, подсказка)
— без единой копии строки шаблона: небольшая карта `SCHEMA_OVERRIDES` называет только
ключи и владельца поля (решение человека / механика рантайма / чужой этап), и тест по
реальным шаблонам эталона требует, чтобы каждый ключ нашёлся. `server/src/artifacts/sheet.ts`
— проводной формат ответа: модель называет значение словом (`ключ: значение`, записи
`- колонка: значение`), кавычки и экранирование `|` ей писать не нужно вовсе.
`server/src/artifacts/applyFill.ts` рисует markdown обратно: рантайм экранирует, нумерует
`claim-N`, нормализует глифы, стирает лишнюю ветку меню — тем же приёмом, что `setDecision`
(«заменяет всё после метки»).

Три точки применения, под одной ручкой `ModelDef.compactForms: 'off' | 'fill' | 'inputs' |
'all'` (умолчание `'off'`, правило «одна ручка на замер» из журнала прогонов):
`'fill'` — `FormFillExecutor` спрашивает по карточке поля вместо строки бланка, плюс
инструмент `FillField` (`exec/tools/index.ts`, MCP-обвязка в `SdkExecutor.ts`) — тот же
гейт и та же политика, что у любой записи: путь резолвится не самим вызовом, а ключом
артефакта через `PolicyContext.stageArtifacts`/`Run.stageArtifacts`, тем же приёмом, что у
внешних MCP-инструментов (`evaluateMcpPaths`). `'inputs'` — входные артефакты
intent/explore/ask/plan (флоу `loop`) и план на входе chunk идут компактной проекцией
(`renderSheet` в `prompt/build.ts`) без потери содержимого — только легенды, цитаты и
разметка таблиц; verify/handoff и патчи получают полный текст всегда. `'all'` — оба эффекта.

Поля, объявленные в `SCHEMA_OVERRIDES` за рантаймом, модели не отдаются и в основном пути
(`FormFillExecutor.modelGroupFields`), а не только в карточном: relog серии v5 показал
выдуманный моделью `base_sha` плана. Исключение действует ТОЛЬКО для шаблонов, чьи поля
рантайма закрывает автозаполнение до модели (`run/formAutofill.ts`: план, готовность,
отчёты разведки и вопросов) — иначе поле осталось бы плейсхолдером, закрыть который
некому; неизвестный факт пишется фактом («н/п — не git-репозиторий»). Скрепа по реальным
шаблонам — `formAutofill.test.ts`: добавляя ключ рантайма в покрытый шаблон, добавь и его
автозаполнение.

Перезапись, стёршая поле решения человека, по умолчанию уходит оператору с нотой
(`destructive.ts`). Ручка `limits.restoreErasedDecisions` (выключена до замера) вместо этого
возвращает поле в содержимое (`repairErasedDecisions`) и отдаёт исполнителю исправленный
вход через `updatedInput` — кроме массовой потери строк. Ручка едет к гейту в
`PolicyContext`, но входом политики не является.

### Конфигурация

`config/runner.json` (порт, оператор, путь к эталону методологии — тексты этапов и
субагенты по умолчанию берутся из его `implementations/claude-code/{skills,agents}`, явные
`skillsDir`/`agentsDir` побеждают, лимиты), `config/models.json` (провайдеры + модели с **руками проставленным** `rank`),
`config/projects/*.json` (корень целевого проекта, профили «этап → модель», бюджет).
`projects/*.local.json` в `.gitignore`. Каталог переопределяется `SDLC_CONFIG_DIR`.
Ключи вида `"// заметка"` — комментарии для человека.

Значения, которые меняются от машины к машине, а не только между проектами, живут ВНЕ
закоммиченных файлов. Два места, приоритет по возрастанию: `config/runner.json` (переносимые
умолчания) → `config/runner.local.json` (эта машина, в `.gitignore`) → переменные окружения.
Правкой закоммиченного файла машинное не задаётся никогда: `SDLC_STATE_DIR` (состояние
рантайма — вердикты попыток), `SDLC_BASH_PATH`, `SDLC_OPERATOR`, `SDLC_SKILLS_DIR`,
`SDLC_AGENTS_DIR`, `SDLC_METHODOLOGY_DIR`, `SDLC_HOST`, `SDLC_PORT`, `SDLC_BROWSE_ROOT`, `SDLC_BENCH_DIR` — и
`<ИМЯ_ПРОВАЙДЕРА>_BASE_URL`/`<ИМЯ_ПРОВАЙДЕРА>_API_KEY` для каждого провайдера в
`config/models.json` (`server/src/provider/registry.ts`). Оба поля провайдера читаются
одним и тем же способом — по имени провайдера в верхнем регистре.

В путях закоммиченного `runner.json` разворачиваются ведущая `~` и `${VAR}` — иначе
«переносимое умолчание» работало бы ровно на одной машине. `operator` там — заглушка
«не задан»: имя уходит в поля решений артефактов, а личное имя в публичном файле это
утечка. Виток с заглушкой не стартует и говорит, что именно задать (`operatorProblem`,
проверка на `POST /api/runs`) — падать при ЗАГРУЗКЕ здесь нельзя, иначе человек не увидит
даже интерфейса, где это написано.

`rank` нужен ровно для одного: **правила рецензента** — модель этапа `verify` обязана быть
любого ранга: независимость рецензирования обеспечивается отдельным агентом и проверяемыми свидетельствами, не сравнением рангов.

## Особенности, о которые легко споткнуться

- **TypeScript исполняется напрямую** (`node --watch src/index.ts`, Node ≥22). Отсюда
  `erasableSyntaxOnly`: никаких `enum`, `namespace`, параметров-свойств в конструкторе.
  Относительные импорты пишутся с расширением `.ts`.
- `exactOptionalPropertyTypes` и `noUncheckedIndexedAccess` включены. Отсюда повсеместная
  идиома `...(x === undefined ? {} : { x })` вместо `x` — это не стиль, это требование
  типов.
- **`\b` в регулярках не работает по кириллице** (граница считается по ASCII). В
  `gatesFile.ts` из-за этого вся обязательная пятёрка молча числилась выключенной; там и
  дальше окончания перечисляются явно: `/^да(\s|[—–-]|$)/`.
- Объектный литерал как словарь имён инструментов давал функцию вместо `undefined` для
  ключей вроде `toString` — в `normalize.ts` для этого используется `Map`.
- Комментарии в этом коде объясняют «почему», и многие фиксируют реальный пойманный дефект.
  Правя такой участок, не удаляй объяснение вместе с кодом — и не добавляй пересказ того,
  что и так видно.

M=~/Code/Agent-SDLC
SDLC_METHODOLOGY_DIR=$M SDLC_SKILLS_DIR=$M/implementations/claude-code/skills \
SDLC_AGENTS_DIR=$M/implementations/claude-code/agents npm test

Так набор идёт без пропусков.

**Сквозной виток на живом репозитории прогонялся многократно — через `bench/`, не вручную.**
`bench/` (см. `bench/README.md`) гоняет фикстурную задачу по всей методологии на реальных
моделях и механически сверяет итог с эталоном — так найдены и исправлены несколько реальных
дефектов раннера (блокировка `explore` на первом проходе, хрупкое сравнение поля «Ветка
витка», утечка личных MCP-коннекторов в сессию flow `sdk`) и задокументирован баг апстрима
(`@anthropic-ai/claude-agent-sdk` issue #376 — канал одобрений рвётся при живущем дольше хода
фоновом Task-субагенте; не наш баг, случается нерегулярно на flow `sdk`, чаще на
`explore`/`chunk`/`verify`). Полный цикл `intent → verify` на `claude-sdk` этим багом всё ещё
может прерваться — устойчиво воспроизводимый режим (без внешних сбоев) сейчас: `--stage
chunk --from-snapshot` на моделях flow `loop` (`ollama`/облачные агрегаторы), уже
использовался для настоящих сравнений моделей (`docs/model-runs.md`).

Быстрый старт: `npm run bench -- --model <id> --probe` (проба tool-calling за секунды) →
`npm run bench -- --all --model claude-sdk:sonnet --make-snapshot <имя> --keep-workspace
--slug <слаг>` (снимок один раз) → `npm run bench -- --stage chunk --model <кандидат>
--from-snapshot <имя> --keep-workspace --slug <слаг>` (дёшево на каждого кандидата). Полное
описание, коды возврата, обе фикстуры (`oversize`/`freeship`) — `bench/README.md`.

Перед долгим прогоном или серией действует **преполётный тест** (`bench/src/preflight.ts`):
среда (файлы задачи, зелёность фикстуры, снимок, контрольный маршрут) + окно контекста
(LM Studio — фактическое, Ollama — наличие тега и зашитый `num_ctx`, ловит классы «мёртвый
тег 404» и «голый тег = 4096») + расширенная проба модели (поверх трёх базовых кейсов —
точный многострочный Edit, честность путей, длинная запись без усечения, правка поля без
перезаписи файла) + банк ответов, лимит ходов против штатного и нижняя граница промпта plan
против окна. Живые режимы (`--stage`/`--all`/`--repeat`/`--make-snapshot`) гоняют его
автоматически и на красном не стартуют; ручной запуск — `--preflight`, осознанный обход —
`--no-preflight`. Лимит ходов стенда по умолчанию штатный (40); явный `--max-turns` снимает и
поэтапные потолки конфига.

Отчёт bench (`report.md`) самодостаточен для разбора отказа: причины остановки, «не
стартовал» с этапом-виновником (`stages/index.ts::stageProducing`, `Run.blockerDetails`), `ok
(рантайм)` по `StageResult.closedBy`, отказы вызовов по классам (`report.ts::classifyDenial`).
Прежде класс отказа приходилось выкапывать из `result.json`.

Не объявляй проверенным то, что не запускал — но теперь есть где запускать, и это стоит
делать перед правкой промпта или политики, не только перед правкой методологии.
## Локальная диагностика моделей перед серией bench

Перед серией сначала сверяй `docs/model-diagnostic-status.md`; после диагностики выполни `npm run bench:diagnostics:status`, чтобы обновить только таблицу по последним JSON-отчётам. Не добавляй описательные итоги; недоступные снимки не считай проблемой модели.

Готовность требует завершённых доступных диагностических кейсов, смысловой проверки по их рубрикам, чистого контроля V00 и обнаружения обоих посевов V01/V02, затем полного цикла пяти задач тем же локальным профилем. Частичное покрытие отмечай явно; 8/15 не означает полную диагностику. Полный цикл `--all` измеряет все семь этапов, включая verify. Диагностический кейс обязательно использует `--stop-after-stage`, иначе контрольные этапы искажают длительность и результат. В паспорте сохраняй фактический локальный endpoint; изменение сервера меняет условия сравнения. Занятость GPU проверяй перед загрузкой; сторонние приложения пользователя не останавливай.

Перед серией запусков на локальных моделях обязательно запусти диагностику для каждой выбранной локальной конфигурации, прежде чем запускать серию задач. Для всех доступных уникальных локальных моделей используй `powershell -NoProfile -ExecutionPolicy Bypass -File bench/run-local-diagnostics.ps1 -Provider all -Repeat 1`; скрипт группирует варианты одной модели, а для LM Studio загружает и выгружает модели по очереди. для выбранной модели — `npm run bench:diagnose -- --model <id>`. Для первичного широкого прохода по всем установленным локальным конфигурациям допускается `--repeat 1`; для отбора кандидатов и сравнительной серии используй стандартные пять повторов. Ориентируйся на `config/models.json` и реально доступные теги Ollama / модели LM Studio. Облачные провайдеры в эту проверку не включай. Сохрани JSON/Markdown отчёты из `bench/results/`, проверь preflight и доступность кейсов; отсутствие валидного входного снимка отмечай как «недоступно», не как провал модели. Если конфигурация диагностику не проходит, сначала разберись, проблема ли это модели, её настроек или среды, и зафиксируй решение перед серией. После изменения исходников, конфигурации модели или локального сервера диагностику повтори.
