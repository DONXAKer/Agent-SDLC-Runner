# Симулятор исполнения Agent-SDLC

Запуск из корня Runner:

```bash
npm run bench:simulate
npm run bench:simulate -- --suite task-loop
npm run bench:simulate -- --suite guided
npm run bench:simulate -- --suite full-flow --output /tmp/sdlc-simulation
```

Нужны зависимости проекта, Node и Git. GPU, сервер модели, ключи API и глобальная установка
скиллов не нужны. `--output` принимает новый или пустой каталог; существующий отчёт не
перезаписывается. По умолчанию отчёт сохраняется в отдельном временном каталоге, путь
печатается в конце. Код возврата: 0 — ожидания выполнены, 1 — сценарий не прошёл
(включая неожиданное исключение внутри него), 2 — ошибка запуска CLI или набора целиком.

`report.md` содержит ожидаемые и фактические исходы и первое нарушение; `report.json` —
машинную сводку, revision/dirty и SHA-256 исходников. `traces/*.json` сохраняют модельные
обмены, результаты команд и наблюдения. Временные проекты удаляются в `finally`.
CLI принудительно создаёт отдельный `SDLC_STATE_DIR`, не использует даже явно заданное
пользовательское хранилище вердиктов и удаляет своё после прогона.

Согласованность с внешним эталоном проверяется отдельно в
`server/test/methodologyTemplates.test.ts`: реальные шаблоны проходят разборщики,
профили сравниваются с поставкой Runner, а инструкции этапов — с резервным профилем.
Каталог задаётся через `SDLC_METHODOLOGY_DIR` или `runner.local.json`; без доступного
эталона эти проверки пропускаются. Сквозная фикстура симулятора использует собственные
минимальные формы и сама по себе не доказывает согласованность двух репозиториев.

## Что проверяется

| Набор | Настоящий код | Граница доказательства |
|---|---|---|
| task-loop | `TaskLoopExecutor`, политика инструментов, правки файлов, отдельные процессы `node --test` | Пилот исполнения задачи. `ready_for_review` не является независимым ревью или человеческой приёмкой |
| guided | JSON-ревью, `GuidedExploreExecutor`, `GuidedProgress`, проверки сохранённых ошибок контрактов | Компонентные сценарии, включая повтор запроса и восстановление. Не полный guided v4 от intent до handoff |
| full-flow | `Run`, драйвер этапов, гейты и хранилище вердиктов через локальный HTTP-двойник модели | Сквозная протокольная фикстура; профиль и фактические этапы сохраняются в трассе |

Сценарии TaskLoop: исправная работа, исправление после красной приёмки, выдуманный PASS,
попытка изменить независимые тесты, запись вне scope, устаревшие свидетельства, бюджет
повторов, отсутствующий ответ человека, отказ среды и потерянное требование. Приёмочные
тесты заранее подготовлены отдельно от модельных ответов и защищены политикой исполнителя.
Они проверяют новое поведение после правок; отдельный baseline проверяет исходную среду.

Guided проверяет повреждённый JSON с успешным ремонтом и с отказом после лимита,
разведку без tool calling с отменой/восстановлением и инвалидацией изменённого источника,
а также два уже сохранённых реальных сбоя моделей из корпуса guided-v4. Последние —
воспроизведение артефактов, а не новый замер GPT-OSS или Ministral.

PASS означает совпадение с **заранее заданным ожиданием**: отказ может быть правильным
результатом. В отчёте отдельно остаётся реальный статус исполнителя. Положительный контроль
обязателен — безусловный отказ всем операциям не считается рабочей защитой.

## Как воспроизвести и исправить сбой

1. Запустить набор и открыть первый FAIL с его трассой. Отделить ошибку сценария,
   дефект реализации и ожидаемый отказ процесса.
2. Добавить минимальный сценарий на границе провайдера с независимым ожиданием,
   затем исправить общий интерфейс/инвариант. Продуктовый код не должен знать id сценария,
   имя модели из записи, путь фикстуры или ожидаемый ответ задачи.
3. Повторить отрицательный сценарий и положительный контроль, затем весь набор и штатные
   тесты затронутого компонента. Не менять ожидаемый исход под ошибочное поведение.
4. Изменения промптов/маршрутизации оценить отдельной живой диагностикой и отложенными
   задачами. Симулятор не доказывает, что реальная модель теперь справляется.

`ScriptedProvider` хранит конечный список ответов. Исчерпание — ошибка стенда, а не
автоматическое «готово». Записи обменов пригодны для точного воспроизведения только при
совпадении запроса, включая контекст и инструменты. После изменения промпта старый ответ
можно использовать как инъекцию известной ошибки, но нельзя называть прогнозом нового ответа.

Версии сравниваются запуском одного зафиксированного набора на двух checkout и сравнением
сводок, а не числом зелёных задач само по себе. Автоматический оптимизатор методологии и
изменение критериев приёмки в процессе прогона не реализованы. Обычные временные каталоги
и проверки политик не являются универсальной OS-песочницей для произвольных программ.

## Проверка самого стенда

```bash
node --import ./server/test/setup-state.ts --test 'bench/test/simulator*.test.ts'
npm run bench:typecheck
```

Продуктовые subprocess-тесты удаляют `NODE_TEST_CONTEXT` из наследуемого окружения:
иначе запуск внутри `node:test` родителя может отключить настоящие дочерние тесты.
Это проверяется сценарием красной приёмки с последующим исправлением.
