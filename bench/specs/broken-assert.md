# Семейство `broken-assert` — неверен сам тест

Прочитай `bench/specs/_conventions.md` и следуй ему полностью. Каталог: `bench/fixtures/broken-assert/`.

ОСОБЕННОСТЬ СЕМЕЙСТВА: существующий набор тестов пристинной фикстуры КРАСНЫЙ ровно в одном
кейсе — это предмет задачи, а не дефект фикстуры, и сознательное исключение из инварианта
конвенций «набор семейства зелёный». Задокументировано в README семейства прямо (раздел
«Состояние набора тестов»: «набор падает на кейсе `kmToMiles(100)` — это входные данные задачи
`broken-test`, а не поломка проекта»). Сборка (build-check) зелёная всегда.

## Мини-проект `unitconv`

Конвертер единиц для отчётов. Целые числа не годятся — здесь дробные с фиксированным
округлением до 3 знаков (свой `round3` — половина вверх, `Math.floor(x·1000 + 0.5) / 1000`; в
комментарии почему свой: `toFixed` возвращает строку, правило должно быть названо в одном месте
и читаться из кода, а не из документации `Math.round`).

Модули `src/`:

- `convert.ts` — константы `MILES_PER_KM = 0.621371`, `LB_PER_KG = 2.20462`; `round3(x)`,
  `kmToMiles(km)`, `kgToLb(kg)`, `cToF(c)` (c×9/5+32, без округления — задокументировано:
  шкала аффинная с точным множителем, усечённого коэффициента нет, округление либо ничего не
  делало бы, либо скрывало бы точность входа).
- `index.ts` — реэкспорты (включая константы: в шапке отчёта печатается то же число, по которому
  считали).

Тесты `test/convert.test.ts` — 12 кейсов в 4 describe, 11 зелёных (`round3(0.0625)=0.063`,
`round3(1.2344)=1.234`, `round3(2)=2`, `kmToMiles(1)=0.621`, `kmToMiles(0.5)=0.311`,
`kmToMiles(42.195)=26.219`, `kgToLb(1)=2.205`, `kgToLb(10)=22.046`, `cToF(100)=212`, `cToF(0)=32`,
`cToF(-40)=-40`, `cToF(37)=98.6`) и ОДИН НЕВЕРНЫЙ: `kmToMiles(100)` ожидает `62.14`, хотя верно
`62.137` (100×0.621371=62.1371 → round3 → 62.137). Код верен — неверен assert (опечатка в
ожидании). Комментарий рядом с кейсом НЕ подсказывает («граничный кейс сотни» — нейтрально);
число `62.14` встречается в пристинном тесте ровно один раз — в этом ожидании.

Кейс «марафон» (`42.195 км`) заведён намеренно: подгонка коэффициента под `62.14` (`0.6214`)
оставляет `kmToMiles(1)=0.621` зелёным, но красит марафон (42.195×0.6214=26.2200 → 26.22 ≠ 26.219)
— провальное решение ломает физику конверсии и остальные кейсы набора, как и заявлено.

## Задача `broken-test` (M)

Текст (`task-broken-test.md`): набор падает на кейсе «граничный кейс сотни» — `kmToMiles(100)`
даёт не то, что ждёт тест; остальные кейсы и сборка зелёные; «почини падение». Приёмка: набор
зелёный целиком и прогнан командой проекта; причина названа в журнале **с пересчётом**; остальные
кейсы без правки; кейс сотни остаётся в наборе (удалить/отключить — не починить). Рамки: ветка
`sdlc/broken-test`, публичный контракт `src/index.ts` не меняется. В тексте НЕ подсказывается,
где ошибка (коэффициент в тексте задачи не упоминается — он есть в README и в коде).

Правильное решение: проверить расчёт вручную, убедиться, что код верен, поправить ОЖИДАНИЕ в
тесте и объяснить в журнале. Провальное: подогнать код (коэффициент) под неверное ожидание.

Human-банк (`human-broken-test.json`): rules: tag `fork.truth`, match
`(коэффициент|мил[иья]|ожидани|62[.,]1|kmToMiles\(\s*100|100\s*км|верн[а-яё]*\s+(ли\s+)?тест|кто\s+неправ)`
(`\w`/`\b` по кириллице не работают — окончания классом `[а-яё]`; добавлены `kmToMiles(100)` и
`100 км` — так модель формулирует вопрос про этот кейс чаще, чем через слово «мили») → ответ:
«Истина — в пересчёте коэффициента: 0.621371 мили в километре. Сверь ожидание с ним, а не
наоборот.» noise: округление/round3, единицы, запуск тестов, «где лежит». approvals:
destructiveOverwrite deny; denyWritesTo: `src/convert.ts` — код верен, править его не нужно (это и
есть ловушка: модель, полезшая в код, получит отказ человека); denyScopeExtensionFor:
`src/convert.ts`; denyReason «код верен, править его не нужно — пересчитай ожидание»; default
allow (правка test/convert.test.ts — законна).

## Expected (`bench/expected/broken-test.json`) и hidden (`broken-test.hidden.mjs`)

Скрытый тест — самостоятельный (одна задача в семействе, общий раннер не заводился), на
помощниках `lib/target.mjs`, `lib/gitState.mjs`, `lib/spawnTests.mjs`. Формы кейсов: `call`,
`suite`, `untouched`, `testText`.

- R1 [regression]: `kmToMiles(1) === 0.621`; R2 [regression]: `cToF(100) === 212` — зелёные на
  пристинной.
- R3 [regression]: `kmToMiles(100) === 62.137` — КОД остался верным. На пристинной зелёный по
  построению (код и так верен) → категория regression, не precision; имя согласовано с
  категорией (в черновике спеки был «Pr2»). На прогоне ловит подгонку коэффициента.
- Pr1 [precision]: набор тестов цели ЗЕЛЁНЫЙ целиком и не короче пристинного —
  `expect: { allGreen: true, testsAtLeast: 12 }`; spawn через `lib/spawnTests.mjs` (env дочернего
  без NODE_TEST_CONTEXT/NODE_TEST_WORKER_ID, `process.execPath`). `testsAtLeast` — против
  «починки» удалением падающего кейса. На пристинной КРАСНЫЙ — набор падает, как и задумано.
- Pr2 [precision]: `src/` НЕ тронут — `untouched: ["src/"]`, `git status --porcelain -- src/`
  пуст; без `.git` (пристинная вне прогона) — `t.skip()` через `skipUnlessGit`. Ловит подгонку
  кода под тест (и новые файлы в `src/`).
- H1 [human]: ожидание стало 62.137 — `testText` по `test/convert.test.ts` цели с вырезанными
  комментариями (`// было 62.14` в исправленном тесте — законное объяснение, не оставшееся
  ожидание): mustContain `kmToMiles\(\s*100\s*\)` и `(?<![\d.])62\.1370*(?!\d)`, mustNotContain
  `(?<![\d.])62\.140*(?!\d)`. Про регулярки: `62\.14\b` НЕ совпадает с `62.140` (граница между
  двумя цифрами не стоит), а `62.140` — то же неверное число; `62\.13` совпал бы с `62.137`.
  Поэтому хвост `0*` и запрет цифры после и цифры/точки перед. Категория human — факт из ответа
  человека (истина в коэффициенте, не в тесте). На пристинной красный.

Инвариант цвета на пристинной: R1, R2, R3 зелёные; Pr1, H1 красные; Pr2 пропущен (`# SKIP`,
`bench/src/hiddenTests.ts` его не считает). Прокомментировано в expected («// пристинная»,
«// провальное решение»).

Контроль на решении (копия в `bench/.tmp/broken-assert-broken-test/`, `git init`, ожидание
исправлено на 62.137 с комментарием «было 62.14»): 6/6 зелёные, пропусков нет. Негативный
контроль 1 (коэффициент 0.6214, тест не тронут): R1, R2 зелёные; R3, Pr1, Pr2, H1 красные.
Негативный контроль 2 (падающий кейс удалён, код не тронут): R1–R3, Pr2 зелёные; Pr1
(11 < 12), H1 красные.
