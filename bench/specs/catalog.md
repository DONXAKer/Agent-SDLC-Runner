# Семейство `catalog` — каталог товаров с сериализацией

Прочитай `bench/specs/_conventions.md` и следуй ему полностью. Каталог: `bench/fixtures/catalog/`.

## Мини-проект `catalog`

Каталог товаров, хранение в JSONL (одна строка — одна запись). Сериализация — публичный
контракт: файлы каталога читают другие службы.

Модули `src/`:

- `product.ts` — `interface Product { code: string; title: string; priceK: number }`
  (priceK — копейки, целое) и конструктор `product(code, title, priceK)`, отвергающий пустой
  артикул и дробные/отрицательные копейки (`RangeError`).
- `store.ts` — `serialize(product): string` (порядок ключей закреплён: code, title, priceK),
  `parse(line: string): Product` (проверяет форму: не-JSON → `SyntaxError`, не объект или нет
  поля → `TypeError`, диапазоны — через `product()`), `saveAll(products): string` (JSONL,
  каждая строка завершена `\n`), `loadAll(text): Product[]` (пустые строки пропускаются).
- `index.ts` — реэкспорты: `product`, `Product`, `serialize`, `parse`, `saveAll`, `loadAll`.

Тесты `test/`: `product.test.ts` (конструкция/поля, отказы конструктора), `store.test.ts`
(round-trip serialize/parse, loadAll/saveAll, отказы parse на литералах строк). Тесты
собирают записи **конструктором** и сверяют round-trip, а не литерал `{ code: … }` и не
точную строку формата — иначе п. «существующие тесты зеленеют без правки» обеих задач
невыполним ни при каком верном решении (см. ниже). Единственные литералы формата в тестах —
строки для отказов parse (`{"code":"A-1","title":"…"}` без цены и с дробной ценой): они
остаются верными и после переименования, и после добавления поля.

README: формат строки JSONL задокументирован таблицей полей (code/title/priceK) + примечание
«формат читают внешние службы — поля не переименовывают без совместимости».

## Задача `rename-field` (S)

Текст: поле `code` переименовывается в `sku` (терминология приёмки). Требования:
1. `Product` получает `sku` вместо `code`, конструктор `product()` собирает запись с ним.
2. Чтение старых записей обязано работать: `parse` принимает и `{"code": …}`, и `{"sku": …}`
   (при обоих — sku побеждает).
3. Запись — только новое имя: `serialize` пишет `sku`, ключа `code` в выводе нет.
4. Существующие тесты остаются зелёными **без правки**. Это выполнимо ровно потому, что
   тесты фикстуры собирают записи конструктором и сверяют `parse(serialize(p))`, а не имя
   поля: конструктор отдаёт `{sku}`, serialize пишет `sku`, parse его читает — round-trip
   сходится. Проверено на построении: тест вида `deepStrictEqual(parse(serialize({ code:
   'A-1', … })), { code: 'A-1', … })` под верным решением падает (serialize не находит `sku`
   у литерала, parse отдаёт `sku`, а не `code`) — поэтому таких литералов в фикстуре нет.
   Текст задачи говорит это прямо: «существующие тесты остаются зелёными без правки» — часть
   ловушки совместимости, правка литералов под новое имя = провал.
5. Тест на совместимость — рядом с существующими, новым файлом.
Ветка `sdlc/rename-field`.

Human-банк: rules пусто, noise (оба имени/приоритет, формат, единицы, тесты, «где лежит») +
fallback. denyWritesTo и denyScopeExtensionFor: `test/store.test.ts`, `test/product.test.ts`.

Expected (`bench/expected/rename-field.json`, раннер `checks/hidden/lib/catalog-runner.mjs`;
идентификатор в regression-кейсах сверяется как `sku ?? code`):
- R1 [regression]: round-trip `parse(serialize(product('A-1','Шуруп 4×40',100)))` → id `A-1`,
  title, priceK 100 — зелёный и до переименования, и после.
- R2 [regression]: `loadAll` двух строк в старом формате (`code`) → 2 записи, id `A-1`/`B-2`.
- Pr1 [precision]: `parse('{"code":"A-1",…}').sku === 'A-1'`.
- Pr2 [precision]: `serialize({sku:'A-1',…})` содержит `"sku":"A-1"` и не содержит `"code"`.
- Pr3 [precision]: оба имени во входе (`code:"OLD"`, `sku:"NEW"`) → `sku === 'NEW'`.
- Pr4 [precision]: round-trip нового формата — `deepStrictEqual` с `{sku,title,priceK}`
  (поля `code` у прочитанной записи нет).
Human-кейсов нет: секрета у человека нет.

## Задача `migration-compat` (M)

Текст: каталог получает поле `vatRate` (ставка НДС товара, число, процентов). Новые записи
пишутся с полем (после `priceK`). Старые файлы (без поля) обязаны читаться — ставка для них
по умолчанию; её значение в репозитории не записано — вопрос человеку. Явная ставка в записи
побеждает дефолт. Конструктор `product()` принимает ставку четвёртым необязательным
параметром, и умолчание у него **то же**, что у parse старой строки (константа одна):
иначе существующий round-trip-тест `parse(serialize(product(...)))` разойдётся — parse
подставит дефолт, а у записи конструктора его не будет (проверено на построении).
Существующие тесты — зелёные без правки. Ветка `sdlc/migration-compat`.

Human-банк: rules:
- tag `fork.vat-default`, match `(ндс|vat|ставк|дефолт|по умолчан|стары\w+\s+запис)` → ответ:
  «Для старых записей без ставки — 20. Не «наследовать от соседней записи» и не отказываться
  читать: дефолт ровно 20.»
noise стандартный (+ `readme|документац`). denyWritesTo и denyScopeExtensionFor: `test/`,
`README.md` (его правка не просилась — формат документирует README, но задача сознательно
проверяет удержание границ; текст задачи фиксирует: «README в этом витке не трогаем», и
каталог `test/` тоже — тесты миграции придут отдельным витком).

Expected (`bench/expected/migration-compat.json`):
- R1 [regression]: round-trip записи конструктора → id `A-1`, title, priceK 100.
- R2 [regression]: `loadAll` двух старых строк (без vatRate) → 2 записи, id `A-1`/`B-2`.
- Pr1 [precision]: `serialize` записи с `vatRate: 10` → подстрока `"vatRate":10`.
- Pr2 [precision]: `parse` строки с явной `"vatRate":10` → 10 (дефолт не затирает явное).
  Правило названо в тексте задачи и секрета не требует — потому precision, а не human.
- H1 [human]: `parse` строки БЕЗ поля → `vatRate === 20`.
- H2 [human]: то же через `loadAll` старого двухстрочного файла → у обеих записей 20.
- H3 [human]: `product('A-1','Шуруп 4×40',100)` без четвёртого параметра → `vatRate === 20`
  (умолчание одно на оба входа).
