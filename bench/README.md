# Бенчмарк моделей

Прогон одной и той же фикстурной задачи по витку методологии на разных моделях, с фиксацией
статуса и метрик каждого этапа и механической сверкой итога с эталоном.

Зачем: записи `docs/model-runs.md`, собранные вручную, каждая по своей задаче на своём
проекте. «Модель не тянет этап 5» там неотделимо от «задача была другая». Здесь старт у всех
моделей побайтово одинаковый, а вывод делает код, а не глаз.

## Быстрый старт — как реально гонять

Три инструмента, по возрастанию цены. Дорогой смысл имеет только после дешёвого.

### 1. Проба — секунды, без витка

Отвечает на один вопрос: доходит ли модель до вызова инструмента вообще. Не про фикстуру и
не про методологию — только `provider` + `params` записи модели, три микро-кейса.

```bash
npm run bench -- --model ollama:qwen3:8b-ctx16k --probe
```

Красная проба — модель не тянет этап 5 почти наверняка, дальше не тратимся. Зелёная зелёного
этапа не обещает — это скрининг, не измерение. Проба меряет только флоу `loop` (провайдер
должен идти этим флоу — `claude-sdk` пробой не измерить, ему это и не нужно).

### 2. Снимок — один раз, платно, на сильной модели

Снимок замораживает рабочую копию сразу после названного этапа (по умолчанию — `plan`):
дальше все модели-кандидаты получают побайтово одинаковый вход, а `intent → … → plan`
оплачивается один раз, не на каждом кандидате.

```bash
npm run bench -- --all --model claude-sdk:sonnet \
  --slug snap-oversize --keep-workspace \
  --make-snapshot oversize-plan
```

`--snapshot-after <этап>` меняет точку снимка, если нужно сравнивать кандидатов не с `chunk`,
а с более раннего или более позднего этапа. Снимки лежат в `bench/snapshots/<имя>/` — это
полные копии рабочих деревьев конкретной машины, в `.gitignore`, снимай заново на новой машине
или после правки промптов/фикстуры (иначе сравнение станет нечестным — «то же самое», а не
«то же самое, посчитанное заново»).

### 3. Кандидат — дёшево, со снимка

```bash
npm run bench -- --stage chunk --model polza:qwen3-14b \
  --slug bench-qwen3-14b --keep-workspace \
  --from-snapshot oversize-plan
```

Стартует сразу со следующего этапа после точки снимка (`chunk`, если снимок сделан после
`plan`) — `intent`/`explore`/`ask`/`plan` не повторяются и не оплачиваются. Пишет
`bench/results/<slug>.json` и `.report.md` (щупы, метка «опасна», код возврата) и печатает
черновик записи для `docs/model-runs.md` — вклеивать и дописывать «Что тюнить»/«Вердикт»
руками, бенчмарк журнал не дописывает сам.

### 4. Посев — единственный способ померить, сколько рецензент ПРОПУСКАЕТ

```bash
npm run bench -- --stage verify --model polza:ministral-14b \
  --from-snapshot min14-clean --seed swallow-tariff-error --slug bench-seed-1
```

Ключ `--seed` вносит в рабочую копию дефект известного класса поверх готового сэмпла
этапа 5 и меряет, назван ли он на этапе 6 — гейтом или отчётом рецензента. Без этого
«рецензент ничего не нашёл» и «находить было нечего» — одно и то же наблюдение; журнал
признаёт пробел прямо (r18: самоценз мерялся на сэмпле 9/9, «пропускать было почти
нечего»).

- Классы посева — `bench/src/seeds.ts`; `--seed none` — контрольный прогон без посева, им
  меряются ложные срабатывания.
- Посев допустим только с `--from-snapshot` и `--stage verify`: если прогон сам проходит
  chunk, исполнитель увидит дефект как свой код и вправе его починить.
- Дефект вносится в файл ФИКСТУРЫ (не в написанное моделью) — стенд обязан быть
  побайтово одинаковым для всех измеряемых моделей. Не найден якорь — прогон падает, а не
  идёт без дефекта.
- **Код возврата у прогона с посевом означает другое**: `0` — дефект назван, `1` — пропущен
  (у `--seed none` наоборот: `0` — ложных срабатываний нет). Зелёный вердикт здесь
  недостижим по построению, и судить по нему было бы нечем.

### Полный цикл на одной модели

Без снимка — весь виток на одной измеряемой модели (`verify` всегда идёт по контрольному
маршруту, см. «Ограничение» ниже):

```bash
npm run bench -- --all --model claude-sdk:sonnet --slug bench-control --keep-workspace
```

Дороже и медленнее, чем снимок + кандидат — оправдано для калибровки самой фикстуры (шаг 4
`ROADMAP.md`) или для модели, которую сравнивать больше не с чем.

### Задачи и семейства фикстур

`--task <id>` выбирает задачу из реестра `src/tasks.ts` — 32 задачи в 14 семействах, по
каталогу фикстуры на семейство: общая `fixture/` (`parcel-price`: `oversize` — умолчание,
`freeship`) и `fixtures/<семейство>/` для остальных. Флаг влияет на всё: файл задачи, банк
ответов человека, эталон, скрытые тесты. Снимок помнит свою задачу (`snapshot.json`), и
`--from-snapshot` с чужим `--task` отвергается до копирования дерева — иначе банк ответов и
скрытые тесты одной задачи легли бы на дерево другой, и все кейсы были бы красными при
исправной модели. Задача, чей каталог ещё не построен, даёт код `2` и причину, не стек.
Полный список, по семействам, стоит в справке — она печатается при любой ошибке ключей
(например, `npm run bench` без `--model`, код 2). Что каждое семейство меряет — раздел
«Фикстуры» ниже.

```bash
npm run bench -- --model ... --probe --task vat-rounding
```

### Коды возврата

`0` — прошла, `1` — измерение состоялось и модель не прошла, `2` — измерение НЕ состоялось
(упало средой/конфигом, а не модель показала себя). У пробы и полного бенчмарка одна и та же
логика: средовой/сетевой сбой не красит модель. Исключение — прогон с `--seed`: там `0`/`1`
означают «дефект назван / пропущен» (см. выше).

## Состояние

Готово: 14 семейств фикстур и 32 задачи (реестр `src/tasks.ts`, спеки — `specs/`),
автоответчик человека, драйвер витка, коллектор, снимки, проба, посев дефекта (`--seed`),
эталон и скрытые тесты каждой задачи, отчёт с шестью щупами (плюс седьмой — находимость,
когда шёл посев) и меткой «опасна», черновик записи в `docs/model-runs.md`. Живой прогон
работает — использовался для настоящих сравнений моделей (`docs/model-runs.md`) на задачах
`oversize`/`freeship`; **остальные задачи живьём ещё не гонялись** — у них нет ни снимков,
ни контрольного прогона на сильной модели, и первый замер каждой — это калибровка задачи,
а не модели (шаг 4 `ROADMAP.md`).

Подробности по шагам, устройству и открытым долгам — `ROADMAP.md`.

## Как устроено

| Каталог | Что |
|---|---|
| `fixture/` | Мини-проект `parcel-price` + `.sdlc/gates.md` + `task*.md` + `human*.json` (задачи `oversize`, `freeship`). Копируется в tmp целиком. |
| `fixtures/<семейство>/` | Остальные мини-проекты, по одному на семейство; внутри — то же, что в `fixture/`: `task-<id>.md`, `human-<id>.json` на задачу. |
| `specs/` | Спеки семейств (`_conventions.md` — общие правила постройки): что за проект, какие задачи, какие ловушки, какие кейсы эталона. Роадмап фикстур и его протокол. |
| `src/tasks.ts` | Реестр задач: id → каталог фикстуры → файлы. Единственное место, откуда `--task` узнаёт задачу. |
| `expected/` | Эталонные значения скрытых тестов, `<id>.json` на задачу. |
| `checks/hidden/` | Скрытые тесты `<id>.hidden.mjs` — вне фикстур, в рабочую копию не копируются. `lib/` — общее: интерпретаторы эталона семейств, цель и эталон, спавн набора тестов цели, состояние git-дерева, файловые кейсы. |
| `src/` | Обвязка: аргументы, маршруты, рабочая копия, снимки, проба, драйвер, отчёт, CLI. |
| `test/` | Герметичные тесты обвязки. Входят в общий `npm test`. |
| `control.json` | Контрольный маршрут «этап → модель». |
| `baseline/` | Замороженные контрольные прогоны — в репозитории. |
| `results/` | Результаты и отчёты прогонов — **в репозитории** (`docs/model-runs.md` ссылается на них, без них вердикты не перепроверить). |
| `snapshots/` | Снимки рабочих копий — в `.gitignore` (машинно-специфичны, снимай заново на новой машине). |

Сам бенчмарк в `npm test` не входит: он стоит денег и минут, ходит в сеть, недетерминирован
по построению и требует эталона методологии на диске. Красный бенчмарк не означает регрессию
раннера.

## Ограничение, которого не обойти

Правило рецензента требует строго `rank(verify) > rank(chunk)`. **Прогнать одну модель на всём
витке невозможно**: этап 6 всегда идёт по более сильному маршруту. Режим `--all` означает
«измеряемая модель везде, кроме `verify`», и читать его иначе нельзя. Попытка измерить слабую
модель на `verify` даёт «профиль не собрался» и код 2 — это «не измерено по правилу
рецензента», а не отказ модели.

## Что бенчмарк НЕ меряет

- **Артефакты бенч-витка подписаны автоответчиком** под именем «Бенчмарк». Их нельзя
  коммитить и нельзя выдавать за пройденный виток.
- **Автоответчик разрешительнее живого оператора.** Он говорит «да» почти всему, отказывая
  только по декларации `human-<id>.json` задачи. Результат — верхняя оценка, а не поведение в
  бою; все его решения обязаны попадать в отчёт, чтобы зелёный, полученный чужим «да», читался
  как таковой.
- **`friction` есть только у флоу `loop`.** `SdkExecutor` не считает ни повторов, ни битого
  JSON, ни отказов политики. В отчёте это «не изм.», никогда не ноль.
- **При `costUsd === null` бюджет не действует вообще.** На локальных провайдерах
  ограничителями остаются ходы и стенные часы, и это пишется в каждый такой отчёт. У рублёвых
  агрегаторов (`polza`, `alltokens`) провайдер знает свою валюту (`registry.ts`) — но апстрим
  бывает нестабилен сам по себе (502 и подобное), это не находка о модели.
- **Меряется связка**, а не модель: модель + промпты методологии + набор гейтов + раннер.
  Смена любого звена меняет результат — снимок и контрольный прогон переснимаются после
  каждой правки промптов, рантайма или фикстуры.
- **Одна экосистема.** Фикстуры — node/TS. На C#, Python и Unreal поведение гейтов, детект
  сборки и размер промпта другие.
- **Один прогон — наблюдение, а не измерение.** Модели с высокой дисперсией (замечено на
  `ministral-14b`) дают заметно разные исходы между прогонами при той же настройке — мерить
  такие сериями ≥3, не одним прогоном. Записывать надо все наблюдения, а не усреднять.
- **Flow `sdk` (claude-sdk) подвержен известному внешнему багу** Agent SDK
  (`anthropic-ai/claude-agent-sdk-typescript#376`): канал одобрений может оборваться, если
  фоновый Task-субагент переживает конец хода модели. Не наш баг, воспроизводится нерегулярно
  (замечено чаще на `explore`/`chunk`/`verify`). Локальные и облачные (`polza`, `ollama`)
  модели идут флоу `loop` и этому не подвержены.

## Фикстуры

Четырнадцать мини-проектов без зависимостей (TypeScript исполняется напрямую, Node ≥ 23.6),
каждый со своим набором гейтов и своими задачами. Первая, `parcel-price`, меряет доведение
фичи и удержание факта из диалога; остальные заведены под то, чего одна фича не показывает:
отказ от вредного, нулевое изменение как правильный ответ, ложная атрибуция бага, чужой
контракт, документация, которая врёт. Подробно — `specs/<семейство>.md`.

| Семейство | Задачи | Что меряет сверх «сделала ли фичу» |
|---|---|---|
| `fixture` (`parcel-price`) | `oversize`, `freeship` | ставка из ответа человека, разрушающая перезапись, граница плана |
| `billing` | `vat-rounding`, `add-validator`, `config-default`, `silent-contract` | льгота из ответа человека, ложные вопросы, полнота правки конфига, необязательный параметр без слома формы |
| `payments-mock` | `external-contract` | реализация по чужому контракту (змеиный регистр, сумма строкой, отказ при HTTP 200) |
| `ledger` | `perf-keep-behavior`, `contradiction`, `refuse-dangerous`, `multi-file-cascade`, `zero-change-verify` | оптимизация без смены поведения, противоречие в ТЗ, отказ на разрушение, каскад по файлам, посев для рецензента |
| `cli-tool` | `cli-flag`, `scope-bait`, `plan-only-trap` | приманка вне scope, ложная атрибуция бага в ТЗ |
| `booking` | `tz-deadline`, `two-right-answers` | часовой пояс как секрет человека, две допустимые архитектуры |
| `notify` | `idempotent-retry`, `security-bait`, `silent-partial` | ТЗ требует вредного (ПДн в журнал), честное частичное выполнение |
| `catalog` | `rename-field`, `migration-compat` | совместимость сериализации, запрет трогать README |
| `warehouse` | `impossible-without-data`, `ghost-requirement` | правильный вопрос против выдуманного числа, требование к несуществующей сущности |
| `legacy-docs` | `docs-sync`, `characterization` | нулевое изменение кода: правится документация / пишутся тесты |
| `feature-present` | `already-done`, `undo-feature` | фича уже есть — не писать код; удалить фичу, сохранив контракт |
| `broken-assert` | `broken-test` | неверен сам тест, код верен — набор фикстуры красный по дизайну |
| `flaky-test` | `flaky-by-design` | настоящее мигание (`Math.random`) — набор фикстуры мигает по дизайну |
| `billing-bug` | `bug-by-symptom`, `wrong-diagnosis` | локализация по симптому, ТЗ клевещет на верный модуль |

Нетронутая фикстура обязана быть зелёной сама по себе — для всех семейств, кроме двух
последних исключений по дизайну (`broken-assert`: ровно один падающий тест; `flaky-test`:
падает примерно в 40 % прогонов), что записано в их README и спеках:

```bash
cd bench/fixtures/<семейство>      # или bench/fixture
node scripts/build-check.mjs      # модули собираются
node --test "test/**/*.test.ts"   # существующие тесты — зелёные, не про задачи бенчмарка
```

Красная фикстура означает сломанный бенчмарк, а не плохую модель. Второй инвариант — на
нетронутой фикстуре скрытые тесты задачи дают regression-кейсы зелёными, precision/human —
красными (иначе они мерили бы то, что и так готово); третий — на решении, написанном
человеком по тексту задачи и банку ответов, все кейсы зелёные. Оба гоняются при постройке
семейства (`specs/_conventions.md`), не в `npm test`.

### `parcel-price` — общая база задач `oversize` и `freeship`

Расчёт цены доставки: тарифная таблица по зонам и весу, скидка лояльности, деньги в
копейках.

### `oversize` (умолчание) — надбавка за негабарит

`fixture/task.md`. Щупает модель с четырёх сторон:

| Щуп | Чем задан |
|---|---|
| правка + новый файл + новый тест с реальным прогоном | `priceFor` получает поле, правило живёт отдельным модулем, на него есть тест |
| граница плана | `src/discounts.ts` выглядит уместным местом правки, но задача закрывает вопрос прямо |
| разрушающая перезапись | `src/tariffs.ts` обязан быть в плане, а правка в нём — на несколько строк из полутора сотен |
| вопрос человеку | ставка для суммы измерений свыше 300 см не записана нигде: её нельзя вывести, только спросить |

### `freeship` — бесплатная доставка для крупных отправлений

`fixture/task-freeship.md`. Та же фикстура, ловушки и точка правки НАМЕРЕННО переставлены
местами относительно `oversize` (проверяет, что шкала переносится, а не подогнана под одну
задачу):

| Щуп | Чем задан |
|---|---|
| правка + новый файл + новый тест | правило льготы — отдельный модуль, интеграция — через `discountFor` (не новое поле `Quote`) |
| граница плана | `src/tariffs.ts` трогать не нужно вовсе — тем не менее выглядит уместным местом |
| разрушающая перезапись | риск теперь в МАЛЕНЬКОМ файле (`src/discounts.ts`, полсотни строк) — переписать функцию целиком, а не потерять сотни строк |
| вопрос человеку | существование и порог второй ступени лояльности (`silver`) не записаны нигде |

Живая калибровка `freeship` не завершена чисто (см. «Долги» в `ROADMAP.md`) — фикстура и
скрытые тесты герметично проверены, но ни один живой прогон не дошёл до `verify`.
