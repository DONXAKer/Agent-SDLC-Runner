# Канонизация кодов позиций

Коды позиций приходят с приёмки в разнобой: « az-123 », «AZ-123», «Az-123 » — сканер, ручной
ввод и выгрузка поставщика пишут их по-разному. В таблице `STOCK_TABLE` коды заведены
канонически — верхний регистр с дефисом, — поэтому грязный код не находится: резерв
отказывает «позиции нет», хотя она лежит. Нужна канонизация на границах пакета.

## Что должно получиться

1. Каноническая функция `canonSku(sku: string): string` — обрезка пробелов по краям и
   верхний регистр, ничего больше. Живёт в новом или существующем модуле `src/` и
   реэкспортируется из `src/index.ts`.
2. Канонизация применена на **всех** границах, принимающих код позиции, — так, чтобы грязный
   код везде отвечал как канонический:
   - поиск: `findEntry` (и через него `stockOf`, `totalQty`);
   - резерв: `reserve` и `reservedFor`;
   - ключ записи: `keyFor` (`src/keys.ts`) — `RESERVED` считается по **каноническому** ключу,
     `keyFor('wh-msk', 'az-123 ')` и `keyFor('wh-msk', 'AZ-123')` обязаны совпасть;
   - отчёт: `stockReport` показывает канонические коды.
   Часть этих мест по имени поля не находится — ключ собирается шаблоном; искать надо по
   назначению, не по слову `sku`.
3. Возвращаемые данные — как в таблице: `findEntry('wh-msk', ' az-123 ')` возвращает запись с
   `sku: 'AZ-123'`, а не с грязным кодом.
4. Строки `STOCK_TABLE` не меняются — они уже канонические.
5. На новое поведение есть тест рядом с существующими (`test/`), и набор тестов прогнан
   по-настоящему командой проекта. В журнал этапа идёт то, что напечатала команда.
6. Существующие тесты остаются зелёными и **без правки**: они зовут функции с каноническими
   кодами, для них ничего не меняется.

## Рамки

- Ветка витка заведена: `sdlc/multi-file-cascade`. Виток полный — мелким контуром не закрывать.
- `README.md` не трогаем: договорённости пакета не меняются, канонизация — про вход, а не
  про правила.
